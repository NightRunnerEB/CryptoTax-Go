# JWT + RequestAuthentication: теоретическая справка

Данный документ предназначен для подробного объяснения того, каким образом в архитектуре `CryptoTax` организуется проверка JWT-токенов на уровне Istio, какую роль в этом процессе играет `auth-svc`, зачем системе нужен `JWKS` endpoint и каким образом результат проверки токена превращается в доверенный identity-контекст для backend-сервисов.

Внимание сосредоточено на следующей задаче: пользователь проходит аутентификацию в `auth-svc`, получает `access token`, затем обращается к API через `istio-ingressgateway`, а Istio должен проверить этот токен до попадания запроса во внутренние сервисы. Именно для этого в систему добавляются `JWKS`, `RequestAuthentication`, дополнительные `AuthorizationPolicy` и правила передачи claims в HTTP headers.

Важно сразу зафиксировать ключевую идею. В рассматриваемой модели backend-сервисы больше не должны доверять identity headers, пришедшим напрямую от frontend-приложения. Вместо этого они должны опираться на headers, сформированные самим ingress-прокси Istio уже после успешной криптографической проверки JWT. Иными словами, frontend передаёт только bearer token, а доверенный identity-контекст формируется на границе mesh.

## 1. Общая проблема и архитектурная цель

### 1.1. Проблема клиентских identity headers

Браузерный клиент не должен считаться источником истины относительно собственной идентичности. Любой заголовок, сформированный на стороне frontend, при отсутствии дополнительной проверки может быть подделан.

Из этого следует важный вывод: наличие в HTTP-запросе каких-либо identity headers ещё не означает, что им можно доверять. Следовательно, если backend опирается на такие заголовки напрямую, то он принимает решение о доступе на основании данных, предоставленных недоверенной стороной.

### 1.2. Целевая модель

Целевая модель выглядит иначе:

1. пользователь проходит login через `auth-svc`;
2. `auth-svc` выдаёт подписанный `access token`;
3. frontend при вызове API передаёт только `Authorization: Bearer <token>`;
4. `istio-ingressgateway` проверяет токен;
5. после успешной проверки Istio извлекает нужные claims и копирует их в доверенные headers;
6. backend-сервис получает не просто сырой запрос от браузера, а запрос, прошедший через слой криптографической валидации.

Таким образом, identity переносится из модели «frontend сообщает системе, кто он такой» в модель «система сама проверяет токен и определяет, кто именно выполняет запрос».

## 2. Роль `auth-svc` в этой схеме

`auth-svc` отвечает за login и выпуск токенов доступа. Значит, именно он формирует claims, которые затем используются на уровне Istio и backend-сервисов.

Иными словами, `auth-svc` является доверенным издателем (`issuer`) JWT. Если токен подписан приватным ключом `auth-svc`, а его подпись успешно проверена по публичному ключу, система может считать claims внутри токена достоверными.

### 2.1. Что содержит access token

В текущей конфигурации access token содержит стандартные и прикладные claims:

1. `sub` — идентификатор субъекта;
2. `jti` — идентификатор самого токена;
3. `iss` — issuer токена;
4. `aud` — audience токена;
5. `sid` — идентификатор сессии;
6. `iat` — время выпуска;
7. `exp` — время истечения;
8. `role` — строковое значение роли.

С архитектурной точки зрения особенно важны три значения:

1. `sub`, поскольку именно он временно используется как источник заголовка `x-tenant-id`;
2. `role`, поскольку он переносится в `x-role`;
3. `sid`, поскольку он остаётся полезным для серверной session-модели и logout/refresh flow.

Следовательно, access token одновременно решает две задачи: служит bearer-подтверждением identity для ingress-проверки и остаётся контейнером контекста, который может быть использован внутри платформы.

### 2.2. Почему `role` был переведён из массива в строку

Ранее роль могла представляться как массив `roles`. В рамках текущей интеграции модель была упрощена, так как `outputClaimToHeaders` корректно работает с простыми scalar-claim значениями:

1. строка;
2. число;
3. логическое значение.

Массивы здесь не поддерживаются. Поэтому для текущего этапа выбрано представление `role: String`, например `user`.

## 3. Зачем нужен `JWKS` endpoint

### 3.1. Проблема проверки подписи на стороне Istio

Чтобы Istio мог проверить JWT, ему нужен публичный ключ издателя.
Если бы ключ был единственным и статическим, теоретически его можно было бы жёстко зашить в конфигурацию. Однако такой подход быстро становится неудобным:

1. усложняет rotation;
2. требует ручного обновления конфигурации при смене ключа;
3. плохо соответствует стандартной JWT/JWKS-модели.

### 3.2. Что такое JWKS

`JWKS` (`JSON Web Key Set`) — это стандартный JSON-документ, содержащий один или несколько публичных ключей, которыми можно проверять подписи JWT. Для RSA-ключа такой документ содержит, в частности:

1. `kty` — тип ключа;
2. `kid` — идентификатор ключа;
3. `use` — назначение ключа;
4. `alg` — алгоритм;
5. `n` — modulus;
6. `e` — exponent.

Следовательно, `JWKS` представляет собой не просто произвольный JSON, а стандартизованный способ публикации набора публичных ключей для JWT-проверки.

### 3.3. Почему endpoint имеет вид `/.well-known/jwks.json`

Путь `/.well-known/jwks.json` является стандартной точкой публикации публичных ключей. Это удобно по двум причинам:

1. он хорошо узнаваем для любой системы, работающей с JWT и OIDC-подобными паттернами;
2. он сразу показывает, что данный endpoint относится не к бизнес-данным, а к инфраструктуре аутентификации.

В рассматриваемой архитектуре `auth-svc` публикует именно этот endpoint, а Istio затем обращается к нему по `jwksUri`.

### 3.4. Что именно публикует наш `JWKS` endpoint

В текущей реализации `auth-svc` хранит RSA-пару ключей и формирует из публичного PEM-ключа JWK-представление. В результате `JWKS` endpoint отдаёт набор ключей, содержащий текущий signing key с согласованным `kid`.

Header также содержит `kid`, следовательно, у Istio появляется возможность:

1. прочитать `kid` из токена;
2. найти соответствующий публичный ключ в `JWKS`;
3. проверить подпись именно тем ключом, который соответствует данному токену.

Именно так между JWT и JWKS устанавливается корректная криптографическая связь.

## 4. Роль `RequestAuthentication`

### 4.1. Общий смысл ресурса

`RequestAuthentication` — это ресурс Istio, который задаёт правила проверки JWT для входящих HTTP-запросов.

### 4.2. Почему он применяется на ingress gateway

В нашей схеме `RequestAuthentication` вешается на `istio-ingressgateway`. Это означает, что токен проверяется на внешней границе mesh. Такой подход даёт несколько преимуществ:

1. все внешние запросы проходят через одну централизованную точку проверки;
2. backend-сервисам не нужно повторно заниматься базовой JWT-валидацией на каждом входе;
3. единая политика аутентификации упрощает сопровождение и контроль поведения системы.

### 4.3. Какие параметры задаются в `RequestAuthentication`

В текущей конфигурации ключевыми являются следующие параметры:

1. `issuer` — ожидаемый издатель токена;
2. `audiences` — допустимая аудитория;
3. `jwksUri` — адрес, по которому Istio получает публичный ключ;
4. `forwardOriginalToken` — признак того, что исходный токен можно сохранить в запросе;
5. `outputClaimToHeaders` — правило переноса claims в headers.

### 4.4. Почему `jwksUri` у нас указывает напрямую на `auth-svc`

В текущей корректной конфигурации `jwksUri` указывает прямо на внутренний сервис:

`http://auth-svc.cryptotax.svc.cluster.local:8085/.well-known/jwks.json`

Это наиболее логичная схема для нашего проекта, поскольку издателем JWT является собственный `auth-svc`, а `JWKS` — это его инфраструктурный endpoint с публичным ключевым материалом.

Однако для такой схемы недостаточно одного только `RequestAuthentication`. По умолчанию Istio может получать `JWKS` не тем способом, который подходит для нашего внутреннего issuer. Поэтому в `istiod` дополнительно включается:

`PILOT_JWT_ENABLE_REMOTE_JWKS=envoy`

Практический смысл этой настройки состоит в том, что `JWKS` начинает забираться Envoy, то есть участником mesh, который умеет работать с внутренним service-to-service трафиком по обычным правилам Istio. После этого direct `jwksUri` на `auth-svc` начинает работать штатно.

Следовательно, итоговая модель у нас такая:

1. `RequestAuthentication` запрашивает `JWKS` напрямую у `auth-svc`;
2. `auth-svc` отдаёт публичный ключевой набор;
3. ingress Envoy использует его для локальной проверки JWT;
4. пользовательские запросы больше не требуют отдельного обращения к `auth-svc` для каждой проверки токена.

В production-сценарии `jwksUri` часто указывает на внешний identity-provider вне кластера. У нас issuer внутренний, поэтому `JWKS` публикуется собственным сервисом внутри кластера, а Istio дополнительно настраивается так, чтобы корректно работать с таким источником.

### 4.5. Как работает `outputClaimToHeaders`

После успешной проверки токена Istio может скопировать отдельные claims в HTTP headers. В текущей схеме используется:

1. `sub -> x-tenant-id`
2. `role -> x-role`

### 4.6. Как система реагирует на битый и пустой токен

Здесь важно различать два сценария.

**Сценарий A: токен передан, но он битый**

Например:

1. подпись неверна;
2. `iss` не совпадает;
3. `aud` не совпадает;
4. токен просрочен;
5. `kid` не найден в `JWKS`.

В этом случае запрос отклоняется уже на этапе `RequestAuthentication`. Istio не сможет построить корректную authenticated identity, и дальнейшая обработка защищённого запроса не продолжится.

**Сценарий B: токен вообще не передан**

В этом случае `RequestAuthentication` не считает запрос автоматически ошибочным. Запрос просто идёт дальше без authenticated identity. Затем уже `AuthorizationPolicy` решает, допустим ли такой запрос:

1. если маршрут публичный — запрос может быть разрешён;
2. если маршрут защищённый — запрос будет отклонён, потому что не появятся `requestPrincipal`, claims и производные headers.

Именно поэтому в общей схеме `RequestAuthentication` отвечает за проверку JWT, а `AuthorizationPolicy` — за решение, можно ли без успешно подтверждённой identity вообще обращаться к конкретному маршруту.

## 5. Роль `AuthorizationPolicy` в JWT-сценарии

### 5.1. Почему одного `RequestAuthentication` недостаточно

Сам по себе `RequestAuthentication` не формулирует политику доступа к маршрутам. Он умеет проверить JWT, но решение о том, какие маршруты публичные, а какие требуют identity, задаётся отдельно.

Именно для этого используется `AuthorizationPolicy`.

### 5.2. Ingress-level авторизация

На ingress создаётся отдельная `AuthorizationPolicy`, которая разделяет запросы на две группы:

1. публичные маршруты;
2. защищённые маршруты.

К публичным маршрутам относятся, например:

1. `/auth/register`
2. `/auth/login`
3. `/auth/refresh`
4. `/auth/verify`
5. `/.well-known/jwks.json`

Их нельзя требовать с bearer token, поскольку именно они участвуют либо в первичной аутентификации, либо в инфраструктуре проверки токенов.

К защищённым маршрутам относятся вызовы бизнес-API. Для них ingress-политика требует:

1. наличие корректного `requestPrincipal`;
2. совпадение `aud`;
3. наличие нужных claims, например `role`.

### 5.3. Backend-level авторизация

После ingress запрос поступает во внутренний сервис уже по mTLS. Однако на этом этапе можно наложить ещё один слой условий. Для этого используются сервисные `AuthorizationPolicy`, которые требуют, чтобы ingress при проксировании передал нужные доверенные headers:

1. `x-tenant-id`
2. `x-role`

Это означает, что backend-сервис принимает ingress-трафик только в том случае, если identity-контекст действительно был сформирован на границе mesh. Самого факта, что запрос пришёл из `istio-system`, недостаточно.

### 5.4. Почему это не заменяет backend-валидацию бизнес-правил

Несмотря на наличие JWT-проверки и policy-layer авторизации, backend-сервис всё равно остаётся ответственным за свои собственные бизнес-инварианты. Например, сервис может дополнительно проверять:

1. совпадает ли идентификатор в маршруте с ожидаемым субъектом;
2. допустима ли конкретная операция для данного пользователя;
3. согласуется ли входящий контекст с доменной моделью.

Следовательно, Istio снимает с backend необходимость решать базовую криптографическую задачу, но не устраняет необходимость в предметной бизнес-логике доступа.

## 6. Полная цепочка запроса

После внедрения `JWKS`, `RequestAuthentication` и `AuthorizationPolicy` полная последовательность выглядит следующим образом:

1. пользователь выполняет login через `auth-svc`;
2. `auth-svc` создаёт session, выпускает `access token` и `refresh token`;
3. frontend сохраняет токены и при вызове API отправляет `Authorization: Bearer <access token>`;
4. запрос приходит в `istio-ingressgateway`;
5. `RequestAuthentication` проверяет JWT по `issuer`, `audience` и `JWKS`;
6. при успехе Istio извлекает `sub` и `role`;
7. Istio копирует их в `x-tenant-id` и `x-role`;
8. ingress `AuthorizationPolicy` проверяет, допустим ли запрос к выбранному маршруту;
9. `VirtualService` выбирает целевой backend;
10. ingress Envoy устанавливает mTLS-соединение к backend sidecar;
11. backend-sidecar проверяет transport-level допустимость через `PeerAuthentication`;
12. backend `AuthorizationPolicy` проверяет источник и наличие доверенных headers;
13. только после этого запрос попадает в контейнер приложения.

Таким образом, bearer token проверяется один раз на границе mesh, а backend получает уже результат этой проверки в нормализованной форме.

## 7. Logout, revoke и ограничения такой схемы

### 7.1. Что именно проверяет Istio

Istio в рамках `RequestAuthentication` проверяет:

1. подпись JWT;
2. issuer;
3. audience;
4. срок действия токена.

Однако Istio не делает онлайн-запрос в Redis или БД `auth-svc`, чтобы узнать, не была ли session отозвана после выпуска токена.

### 7.2. Практическое следствие

Из этого следует важный operational trade-off. Если пользователь выполнил `logout`, а session и refresh chain были отозваны, уже выданный access token всё равно может оставаться валидным до момента истечения `exp`. Следовательно, при чисто stateless JWT-модели logout становится не абсолютно мгновенным, а «эффективным в пределах TTL access token».

### 7.3. Почему так делают в production

Такой подход широко используется в production, поскольку даёт важные преимущества:

1. очень быстрая локальная проверка токена;
2. отсутствие обязательного онлайн-вызова в auth backend на каждый запрос;
3. хорошая масштабируемость ingress и backend-сервисов.

Компенсация достигается за счёт короткого `access token TTL` и stateful `refresh token`. Иными словами, система допускает, что access token может прожить ещё несколько минут после logout, но при этом запрещает дальнейшее обновление session через revoked refresh chain.

### 7.4. Что делать, если нужен жёсткий revoke

Если бизнес-требование требует мгновенного отзыва доступа, одной только модели `RequestAuthentication` недостаточно. В таком случае поверх базовой JWT-проверки обычно вводят online authorization/introspection слой, который:

1. обращается к auth backend;
2. проверяет статус session или token id;
3. запрещает запрос даже при формально валидном JWT.

Это дороже с точки зрения latency, но обеспечивает жёсткий контроль revoke.
