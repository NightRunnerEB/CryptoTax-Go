# Kubernetes + Istio: теоретическая справка

Данный документ предназначен для подробного объяснения того, какие механизмы были добавлены в систему после этапа интеграции `External Secrets Operator`, и каким образом они работают внутри Kubernetes-кластера. Если в части ESO основной акцент делался на синхронизации секретов между внешним хранилищем и Kubernetes, то в части Istio внимание смещается на сетевое взаимодействие сервисов, управление маршрутизацией, шифрование трафика, контроль доступа и обеспечение корректной работы frontend-приложения при обращении к backend API через единый входной адрес.

В рассматриваемой архитектуре Istio выступает в качестве сервисной сетки (`service mesh`), то есть инфраструктурного уровня, который располагается между приложениями и берет на себя значительную часть сетевой логики. В обычной схеме без service mesh каждый сервис должен был бы самостоятельно решать вопросы TLS, сетевых политик, контроля доступа, логирования межсервисного трафика и частично маршрутизации. При использовании Istio эти задачи выносятся из кода приложений в отдельный управляемый слой, что позволяет централизованно задавать правила поведения всей системы.

## 0. Как Istio работает на практике: control plane и runtime

Прежде чем переходить к отдельным ресурсам, необходимо зафиксировать ключевую идею, без которой модель Istio воспринимается ошибочно. Ресурсы `Gateway`, `VirtualService`, `DestinationRule`, `PeerAuthentication` и `AuthorizationPolicy` не являются самостоятельными runtime-компонентами, через которые запрос проходит как через последовательную цепочку сервисов. Они представляют собой декларативные объекты конфигурации, которые хранятся в Kubernetes API и используются control plane Istio для настройки реально работающих прокси Envoy.

Иными словами, внешний запрос не «идёт сначала в `Gateway`, затем в `VirtualService`, затем в `DestinationRule`». На самом деле запрос попадает в ingress Envoy или в sidecar Envoy, а уже этот прокси принимает решение на основе конфигурации, которая была заранее собрана из ресурсов Istio и загружена в него компонентом `istiod`.

### 0.1. Что относится к control plane

Под control plane в рассматриваемой конфигурации в первую очередь понимается `istiod`. Его задача состоит не в передаче пользовательского трафика, а в управлении сетевым поведением mesh. Именно `istiod`:

1. считывает ресурсы Istio из Kubernetes API;
2. анализирует их связи и selectors;
3. формирует итоговую конфигурацию Envoy;
4. передаёт эту конфигурацию ingress gateway и sidecar-прокси.

Следовательно, `istiod` работает как интерпретатор декларативных правил. Пользователь или разработчик создаёт YAML-ресурсы, Kubernetes сохраняет их, а `istiod` преобразует их в рабочие настройки прокси.

### 0.2. Что относится к runtime plane

Под runtime plane следует понимать уже те компоненты, которые реально участвуют в обработке запросов во время работы системы. В нашей архитектуре к ним относятся:

1. `istio-ingressgateway`, принимающий внешний трафик;
2. sidecar `istio-proxy` у backend-сервисов;
3. сами контейнеры приложений.

Именно эти процессы обрабатывают сетевой трафик в реальном времени. Следовательно, если задаваться вопросом «кто фактически принимает решение по запросу», то ответом будет не Kubernetes-ресурс как таковой, а соответствующий экземпляр Envoy, работающий в ingress gateway или в sidecar.

### 0.3. Как именно появляется рабочая конфигурация

После создания ресурсов Istio происходит следующая последовательность действий:

1. YAML-ресурс, например `Gateway` или `VirtualService`, применяется в Kubernetes;
2. Kubernetes сохраняет его как обычный API-объект;
3. `istiod` считывает этот объект из Kubernetes API;
4. `istiod` определяет, к каким ingress или workload-прокси относится данное правило;
5. затем он преобразует набор ресурсов в итоговую runtime-конфигурацию Envoy;
6. эта конфигурация доставляется в нужные Envoy-прокси по служебному каналу управления.

Из этого следует принципиально важный вывод: ресурсы Istio не обрабатывают запросы напрямую, а описывают поведение тех прокси, которые будут обрабатывать запросы позже.

### 0.4. Как внешний запрос проходит через систему

Когда внешний клиент отправляет HTTP-запрос, фактическая последовательность выглядит следующим образом:

1. запрос поступает в `istio-ingressgateway`;
2. Envoy внутри ingress gateway проверяет, соответствует ли запрос допустимому входному listener и host-конфигурации;
3. затем тот же Envoy выбирает маршрут до целевого backend-сервиса;
4. после выбора маршрута запрос отправляется в сторону нужного workload;
5. при этом клиентский Envoy использует правила клиентской политики, например необходимость mTLS;
6. на стороне принимающего Pod входящий sidecar проверяет допустимость transport-level соединения;
7. затем проверяется политика авторизации;
8. только после этого запрос передаётся контейнеру приложения.

Таким образом, в runtime запрос фактически проходит через прокси Envoy, а не через ресурсы Istio как самостоятельные исполняемые сущности.

### 0.5. Почему это важно для правильного понимания

Если не разделять control plane и runtime plane, легко ошибочно представить Istio как последовательность «виртуальных сервисов», которые вызывают друг друга. На практике этого не происходит. `Gateway`, `VirtualService`, `DestinationRule`, `PeerAuthentication` и `AuthorizationPolicy` — это не шаги выполнения запроса, а различные слои конфигурации, которые заранее определяют поведение прокси.

Именно поэтому корректнее мыслить не так:

`запрос -> Gateway -> VirtualService -> DestinationRule -> PeerAuthentication -> AuthorizationPolicy`

а так:

`запрос -> Envoy ingress/sidecar, который уже заранее настроен на основе Gateway, VirtualService, DestinationRule, PeerAuthentication и AuthorizationPolicy`

## 1. Sidecar-инъекция

### 1.1. Общий принцип

Ключевой идеей Istio является то, что рядом с каждым приложением внутри Pod запускается дополнительный контейнер-прокси. Такой контейнер называется `sidecar`, а в рамках Istio он обычно представлен контейнером `istio-proxy`, внутри которого работает Envoy. С точки зрения архитектуры это означает, что приложение больше не взаимодействует с сетью напрямую в чистом виде. Формально оно по-прежнему слушает свой порт и отправляет запросы как обычно, однако реальный входящий и исходящий трафик проходит через sidecar-прокси, который может применять к нему правила маршрутизации, шифрования, авторизации и телеметрии.

Таким образом, sidecar можно рассматривать как промежуточный сетевой слой, встроенный в каждый Pod. Само приложение продолжает оставаться относительно простым: например, `tax-svc` или `aggregation-svc` не обязаны самостоятельно реализовывать mTLS между сервисами, не обязаны знать о сертификатах соседних сервисов и не обязаны самостоятельно принимать решение, допустим ли вызов со стороны того или иного клиента. Все эти функции могут быть переданы в сторону Istio.

### 1.2. Механизм автоматической инъекции

Для того чтобы sidecar появился в Pod, используется механизм автоматической sidecar-инъекции. В Kubernetes это реализуется через `Mutating Admission Webhook`. Смысл этого механизма состоит в том, что при создании нового Pod API-сервер Kubernetes позволяет специальному webhook-модулю изменить исходный манифест Pod до того, как он будет окончательно сохранён и передан на выполнение.

В нашем случае включение автоматической инъекции производится с помощью метки namespace:

`istio-injection=enabled`

После появления этой метки все новые Pod, создаваемые в соответствующем namespace, будут автоматически модифицироваться webhook-ом Istio. В исходный Pod spec добавляются:

1. init-контейнер `istio-init`, который подготавливает сетевую среду Pod;
2. контейнер `istio-proxy`, являющийся собственно sidecar-прокси;
3. дополнительные volumes, переменные окружения и служебные настройки, необходимые для сертификатов, конфигурации Envoy и связи с control plane.

Важно понимать, что речь идёт именно о новых Pod. Если приложение уже было развёрнуто до установки метки `istio-injection=enabled`, то существующие Pod автоматически не изменяются. Именно поэтому после включения инъекции необходимо выполнить пересоздание Pod, например через `rollout restart` Deployment. Только после этого новые Pod будут созданы уже с встроенным sidecar.

### 1.3. Роль init-контейнера

Отдельное значение имеет init-контейнер `istio-init`. Его задача состоит не в обработке бизнес-логики и не в обслуживании запросов, а в подготовке сетевых правил Pod. На практике он настраивает перенаправление трафика при помощи механизмов вроде `iptables`. За счёт этого входящие и исходящие соединения приложения начинают проходить через Envoy.

Следовательно, sidecar не просто «соседствует» с приложением, а реально становится обязательным участником сетевого обмена. Именно за счёт этого Istio получает возможность:

1. шифровать соединения между сервисами;
2. применять маршрутизацию по правилам mesh;
3. собирать сетевые метрики;
4. блокировать неразрешённые вызовы.

### 1.4. Проверка результата инъекции

После корректной инъекции sidecar Pod обычно содержит два основных контейнера:

1. контейнер приложения;
2. контейнер `istio-proxy`.

При просмотре списка Pod это видно по статусу `READY`, например `2/2`. При детальном просмотре Pod через `kubectl describe pod` можно увидеть `istio-init` среди init-контейнеров и `istio-proxy` среди обычных контейнеров. Именно это служит подтверждением того, что workload уже включён в mesh.

## 2. Основные Istio-ресурсы и их назначение

После включения sidecar-инъекции одного только присутствия прокси недостаточно. Необходимо задать правила, по которым этот прокси будет работать. Для этого в Kubernetes создаются специальные ресурсы Istio. Каждый из них отвечает за отдельный аспект сетевого поведения системы.

Прежде чем рассматривать каждый ресурс по отдельности, важно ещё раз зафиксировать принцип их взаимодействия. Эти ресурсы не «вызывают» друг друга напрямую. Они совместно описывают, каким образом должны вести себя ingress и sidecar-прокси. Один ресурс отвечает за входную точку, другой — за маршрутизацию, третий — за клиентскую политику соединения, четвёртый — за допустимость transport-level связи, пятый — за авторизацию уже установленного запроса. Поэтому говорить о них следует не как о pipeline из исполняемых сервисов, а как о системе согласованных слоёв конфигурации.

Соответственно, когда в систему приходит новый запрос, правильнее представлять следующую картину:

1. ingress Envoy принимает запрос;
2. ingress Envoy применяет к нему конфигурацию, собранную из `Gateway` и `VirtualService`;
3. при отправке запроса к backend применяются правила `DestinationRule`;
4. на принимающей стороне sidecar проверяет требования `PeerAuthentication`;
5. затем тот же sidecar проверяет `AuthorizationPolicy`;
6. только после этого трафик доходит до контейнера приложения.

Из этого видно, что сами ресурсы не являются обработчиками трафика. Обработчиком остаётся Envoy, а ресурсы лишь задают ему правила принятия решений.

### 2.1. Что такое `istio-ingressgateway`

Прежде чем разбирать `Gateway`, необходимо отдельно пояснить, что именно представляет собой `istio-ingressgateway`, поскольку без этого сам механизм Istio ingress действительно выглядит неочевидно. `istio-ingressgateway` — это не абстрактная идея и не логический тег, а реальный runtime-компонент, развёрнутый в кластере как обычный Kubernetes `Deployment`. Иначе говоря, в namespace `istio-system` существует стандартный Deployment, который создаёт один или несколько Pod. Внутри этих Pod запускается Envoy-прокси, принимающий внешний трафик и работающий как входная точка в service mesh.

Следовательно, `istio-ingressgateway` по своей природе ничем принципиально не отличается от Deployment бизнес-сервиса. Как и любой другой Deployment, он:

1. хранится в Kubernetes как обычный ресурс;
2. создаёт Pod через ReplicaSet;
3. может иметь один или несколько экземпляров;
4. может быть просмотрен через `kubectl get deployment`;
5. может быть удалён, масштабирован или переустановлен.

Важно при этом понимать, что мы не создавали его собственным YAML-файлом в репозитории. Этот Deployment появился в кластере после установки Istio через Helm chart. Иными словами, его шаблон поставлялся самой системой Istio, а после применения chart был сохранён в состоянии Kubernetes. Поэтому после остановки и повторного запуска кластера Kubernetes не «читает chart заново», а просто восстанавливает уже сохранённые ресурсы из собственного состояния. Helm нужен повторно только в случае переустановки или обновления.

Именно здесь становится понятен смысл поля `selector` внутри ресурса `Gateway`. Когда в `Gateway` указано:

`selector: istio=ingressgateway`

это означает, что конфигурация данного `Gateway` должна применяться к тем Pod, которые уже запущены ingress gateway и имеют соответствующую label. Таким образом, `Gateway` не создаёт ingress Pod и не описывает backend-сервисы напрямую. Он лишь говорит Istio: «вот эта логика приёма внешнего трафика относится к существующим Pod ingress gateway». Уже затем сами ingress Pod, руководствуясь `Gateway` и `VirtualService`, принимают внешний HTTP-трафик и пересылают его в нужный backend-сервис.

Иными словами, связь выглядит так:

1. `istio-ingressgateway` Deployment создаёт ingress Pod;
2. эти Pod имеют label, например `istio=ingressgateway`;
3. ресурс `Gateway` выбирает эти Pod по label;
4. ресурс `VirtualService` задаёт правила, как ingress Pod должен маршрутизировать входящий запрос дальше.

Если удалить `Deployment istio-ingressgateway`, то вход в mesh фактически исчезнет. Ресурсы `Gateway` и `VirtualService` при этом останутся в Kubernetes, однако применять их будет не к чему, поскольку не останется runtime-компонента, принимающего внешний трафик. Восстановление в таком случае выполняется повторной установкой или обновлением соответствующего Helm release Istio.

Также следует понимать, почему ingress gateway может быть не один. Существует два варианта множественности:

1. один Deployment может иметь несколько replicas, и тогда работает несколько одинаковых ingress Pod для отказоустойчивости и балансировки;
2. в кластере может существовать несколько разных ingress gateway Deployment, например для публичного, внутреннего или административного трафика, и тогда разные ресурсы `Gateway` могут ссылаться на разные группы Pod через разные labels.

Таким образом, `istio-ingressgateway` следует воспринимать как обычный технический сервис-посредник, развёрнутый в кластере отдельно от бизнес-сервисов и предназначенный исключительно для приёма внешнего трафика и передачи его внутрь mesh по заданным правилам.

### 2.2. Как `Gateway` влияет на `istio-ingressgateway`

Наиболее важный и при этом наиболее запутанный момент заключается в том, что ресурс `Gateway` не изменяет `Deployment istio-ingressgateway` напрямую. Иными словами, после создания `Gateway` Kubernetes не переписывает YAML Deployment, не добавляет в него новые поля и не пересоздаёт Pod только из-за самого факта появления этого ресурса. Следовательно, влияние `Gateway` на ingress gateway носит не структурный, а конфигурационный runtime-характер.

Механизм работы выглядит следующим образом. После создания ресурса `Gateway` он сохраняется в API Kubernetes как самостоятельный объект конфигурации. Затем компонент `istiod`, являющийся control plane Istio, считывает этот объект из Kubernetes API, анализирует поле `selector` и определяет, к каким именно ingress Pod относится данная конфигурация. После этого `istiod` не меняет Kubernetes Deployment, а преобразует описание `Gateway` в внутреннюю runtime-конфигурацию Envoy.

Именно эта конфигурация затем передаётся в Pod `istio-ingressgateway` по служебному каналу управления, который в Istio основан на механизме xDS. В результате Envoy внутри ingress Pod обновляет своё поведение: начинает слушать нужные порты, учитывать заданные host-правила и быть готовым применять связанную маршрутизацию совместно с `VirtualService`. При этом сам Pod может продолжать работать без пересоздания, если обновление допустимо на уровне горячей перезагрузки конфигурации Envoy.

Таким образом, `Gateway` воздействует на `istio-ingressgateway` не через изменение Kubernetes-объектов уровня `Deployment`, а через передачу новой сетевой конфигурации внутрь уже работающего ingress-прокси. Это принципиально важное различие. `Deployment` отвечает за существование Pod как вычислительной сущности, тогда как `Gateway` отвечает за сетевую логику, которую должен выполнять Envoy внутри этой сущности.

Поэтому полную цепочку влияния корректно описывать так:

1. Helm chart Istio создаёт `Deployment istio-ingressgateway`;
2. этот Deployment создаёт ingress Pod с Envoy;
3. пользователь создаёт ресурс `Gateway`;
4. `istiod` считывает `Gateway` из API Kubernetes;
5. `istiod` генерирует runtime-конфигурацию Envoy;
6. ingress Pod получает эту конфигурацию и начинает работать по новым правилам.

### 2.3. Gateway

Ресурс `Gateway` описывает точку входа трафика в service mesh. Важно не путать его с Kubernetes `Service` типа `LoadBalancer` или `Ingress`. В модели Istio сам `Gateway` является именно декларацией сетевых правил для ingress-прокси, а не отдельным подом или отдельным сервисом. Реальным runtime-компонентом, который принимает входящие подключения, является `istio-ingressgateway`, тогда как объект `Gateway` указывает, какие порты и какие host-правила должны быть на нём активированы.

В нашем случае `Gateway` используется для того, чтобы внешний трафик, приходящий на локальный порт `8080` через port-forward до `istio-ingressgateway`, затем мог быть направлен к нужному backend-сервису. Основные параметры `Gateway` следующие:

1. `selector` — указывает, к каким ingress pod следует применить конфигурацию. Обычно это `istio: ingressgateway`.
2. `servers[].port` — задаёт входной порт и его протокол, например HTTP на порту 80.
3. `servers[].hosts` — определяет, для каких host-ов данный gateway должен принимать запросы.

Иными словами, `Gateway` отвечает за вопрос: через какие входные точки mesh вообще готов принимать трафик.

### 2.4. VirtualService

Если `Gateway` определяет, где трафик принимается, то `VirtualService` определяет, как он должен быть маршрутизирован после приёма. Это один из центральных ресурсов Istio, поскольку именно в нём задаются правила L7-маршрутизации HTTP-запросов.

В `VirtualService` можно описать:

1. какие host-ы и пути должны обрабатываться;
2. в какой сервис и на какой порт направлять запрос;
3. какие дополнительные сетевые политики уровня HTTP следует применить, например CORS.

В нашем проекте изначально использовалась схема host-based routing, где разным сервисам соответствовали разные host-имена, например `auth.cryptotax.local` и `tax.cryptotax.local`. Затем конфигурация была переведена на path-based routing, поскольку frontend должен был обращаться ко всем API через один и тот же адрес `http://localhost:8080`, а различение сервисов стало выполняться по пути:

1. `/auth/*` -> `auth-svc`
2. `/mexc/csv` и `/exchanges/supported` -> `ledger-svc`
3. `/tax/*` -> `tax-svc`
4. `/fiat-currencies`, `/settings`, `/imports/{import_id}/transactions` -> `aggregation-svc`

Ключевые параметры `VirtualService`:

1. `hosts` — host-ы, для которых действует правило.
2. `gateways` — через какой `Gateway` применяется маршрут.
3. `http[].match` — условия срабатывания правила, например по `prefix`, `exact` или `regex`.
4. `http[].route[].destination.host` — целевой Kubernetes Service.
5. `http[].route[].destination.port.number` — порт целевого сервиса.
6. `corsPolicy` — HTTP-политика CORS для браузерных запросов.

Таким образом, `VirtualService` решает вопрос: по какому признаку определить целевой backend и куда именно передать запрос.

### 2.5. DestinationRule

Ресурс `DestinationRule` описывает клиентскую политику при обращении к конкретному сервису-получателю. Если `VirtualService` определяет, куда отправить запрос, то `DestinationRule` определяет, каким образом должен быть организован этот сетевой вызов.

В нашей конфигурации для сервисов были созданы `DestinationRule`, в которых установлен параметр:

`trafficPolicy.tls.mode: ISTIO_MUTUAL`

Это означает, что при обращении к соответствующему сервису sidecar-клиент обязан устанавливать соединение в режиме Istio mTLS. Важно подчеркнуть, что данная настройка относится не к самому приложению, а к Envoy-клиенту, который отправляет запрос от имени приложения.

Дополнительно в `DestinationRule` можно настраивать:

1. стратегию балансировки;
2. connection pool;
3. retries;
4. subsets для версионирования и canary-деплоя.

В нашем MVP-кейсе используется базовая балансировка `LEAST_REQUEST`, однако главным параметром выступает именно `ISTIO_MUTUAL`, поскольку он обеспечивает совместимость с режимом `STRICT` на принимающей стороне.

Следует отдельно подчеркнуть, что `DestinationRule` применяется не только при обычных внутренних вызовах одного backend-сервиса к другому, но и в случае, когда запрос после ingress-маршрутизации отправляется из `istio-ingressgateway` в целевой backend. Причина состоит в том, что ingress Envoy, пересылающий запрос дальше, сам выступает клиентом по отношению к backend-сервису. Следовательно, когда ingress gateway устанавливает исходящее соединение к `auth-svc`, `tax-svc` или другому сервису, он также обязан руководствоваться соответствующим `DestinationRule`, если такое правило определено для данного destination.

### 2.6. PeerAuthentication

`PeerAuthentication` задаёт правила приёма входящих соединений со стороны workload. Если `DestinationRule` определяет, как клиент должен подключаться к сервису, то `PeerAuthentication` определяет, что именно принимающая сторона считает допустимым трафиком.

В нашей системе установлен режим:

`mtls.mode: STRICT`

Это означает, что workload принимает только трафик, пришедший по mTLS через mesh. Любой обычный plaintext-трафик будет отклонён. Практический эффект этого правила был подтверждён: Pod без sidecar, пытающийся обратиться к сервису, не получает корректного ответа и соединение разрывается.

Основные режимы `PeerAuthentication`:

1. `STRICT` — разрешён только mTLS.
2. `PERMISSIVE` — разрешён и mTLS, и plaintext.
3. `DISABLE` — mTLS выключен.

С архитектурной точки зрения `PeerAuthentication` отвечает за вопрос: какие виды соединений вообще разрешено принимать данному сервису.

Важно понимать, что `PeerAuthentication` не включается как отдельный этап уже после завершённого обычного plaintext-соединения. Напротив, его требования участвуют в момент установления transport-level связи. Если клиентский Envoy, руководствуясь `DestinationRule`, пытается установить mTLS-соединение, то принимающий sidecar проверяет, допустим ли такой тип соединения согласно `PeerAuthentication`. Если политика сервера установлена в `STRICT`, а запрос пришёл не по mTLS, соединение не будет считаться допустимым и дальнейшая обработка запроса не продолжится.

### 2.7. AuthorizationPolicy

Ресурс `AuthorizationPolicy` отвечает за контроль доступа после того, как соединение уже установлено. Если `PeerAuthentication` отвечает за то, каким должен быть транспортный уровень соединения, то `AuthorizationPolicy` отвечает за то, может ли данный источник выполнять конкретный запрос.

Иными словами:

1. `PeerAuthentication` говорит: «принимаю только mTLS».
2. `AuthorizationPolicy` говорит: «из допустимых mTLS-клиентов разрешаю только определённые namespace, principals, пути, методы или порты».

В нашей конфигурации используются базовые `ALLOW`-политики, ограничивающие доступ к сервисам вызовами только из namespace `istio-system` и `cryptotax`, а также фиксирующие допустимые порты сервисов. Это уже обеспечивает минимальный уровень сегментации трафика. В дальнейшем данная схема может быть усилена за счёт перехода на `source.principals`, то есть на точное указание конкретных service account, которым разрешено обращаться к сервису.

Ключевые параметры `AuthorizationPolicy`:

1. `selector.matchLabels` — на какие workload распространяется политика.
2. `action` — тип действия, чаще всего `ALLOW` или `DENY`.
3. `rules[].from.source` — откуда разрешён вызов.
4. `rules[].to.operation` — какие порты, методы или пути допустимы.

Следовательно, при корректном рассмотрении runtime-последовательности между этими ресурсами возникает следующая логика. Сначала ingress или клиентский sidecar принимает решение, куда направить запрос, и с какими параметрами должен быть установлен исходящий transport-вызов. Затем принимающая сторона проверяет, допустим ли сам тип соединения с точки зрения `PeerAuthentication`. И только после того, как transport-level соединение признано допустимым, начинается проверка `AuthorizationPolicy`, отвечающей уже не за тип канала связи, а за право конкретного источника выполнять данный запрос.

### 2.8. RequestAuthentication

Ресурс `RequestAuthentication` отвечает за проверку JWT на уровне Istio-прокси. Важно понимать, что это уже не transport-level безопасность, как в случае mTLS, а проверка прикладного токена доступа, который приходит вместе с HTTP-запросом. Если `PeerAuthentication` подтверждает, что трафик пришёл по допустимому защищённому каналу внутри mesh, то `RequestAuthentication` позволяет понять, действительно ли внешний пользователь представил корректный access token.

В нашей конфигурации `RequestAuthentication` применяется к `istio-ingressgateway`. Это означает, что JWT валидируется ещё на входе в mesh, до попадания запроса в backend-сервис. Для такой проверки Istio использует:

1. `issuer` — ожидаемого издателя токена;
2. `audiences` — допустимую аудиторию токена;
3. `jwksUri` — адрес JWKS endpoint, по которому Istio получает публичный ключ для проверки подписи;
4. `forwardOriginalToken` — признак того, что исходный bearer token можно передавать дальше в backend;
5. `outputClaimToHeaders` — правило, по которому отдельные JWT claims копируются в HTTP headers.

В нашем случае это приводит к следующей модели поведения:

1. Istio проверяет подпись токена по публичному ключу из `/.well-known/jwks.json`;
2. Istio убеждается, что `iss` и `aud` совпадают с ожидаемыми значениями;
3. после успешной проверки Istio копирует `sub` в `x-user-id`, а `role` в `x-role`;
4. backend-сервисы получают уже не только bearer token, но и нормализованный набор identity headers, сформированный не frontend-приложением, а ingress-прокси после успешной валидации JWT.

Именно поэтому `RequestAuthentication` следует рассматривать как мост между внешней аутентификацией пользователя и внутренней моделью межсервисного взаимодействия. Он не заменяет `AuthorizationPolicy`, а предоставляет ей достоверную основу: только после успешной проверки JWT можно строить дальнейшие правила допуска по `requestPrincipal`, claims или производным headers.

## 3. Host-based и path-based маршрутизация

### 3.1. Host-based routing

Host-based routing означает, что выбор backend-сервиса зависит от значения HTTP-заголовка `Host`. Например, если запрос приходит на `auth.cryptotax.local`, он направляется в `auth-svc`, а если на `tax.cryptotax.local`, то в `tax-svc`.

Такой подход хорошо подходит для production-сценариев, где у системы есть собственные домены и настроенный DNS. Он позволяет естественным образом разделять API по поддоменам и строить более чистую публичную сетевую схему.

Однако для локальной разработки этот вариант неудобен. Необходимо либо редактировать `hosts`, либо настраивать локальные доменные имена, либо явно передавать `Host` заголовок в каждом запросе. Для frontend-приложения это означает усложнение конфигурации и dev-среды.

### 3.2. Path-based routing

Path-based routing означает, что все запросы приходят на один и тот же базовый адрес, а различение сервисов происходит по URI-пути. Именно этот подход был выбран в текущей frontend-интеграции. С точки зрения пользователя это удобнее, поскольку весь frontend работает с единым API base URL:

`http://localhost:8080`

Далее уже Istio анализирует путь и определяет, в какой сервис направить запрос.

Преимущества такого подхода:

1. единая точка входа для frontend;
2. отсутствие необходимости управлять доменными именами в локальной среде;
3. более простая настройка `.env` на стороне UI.

Недостаток состоит в том, что правила маршрутизации становятся более чувствительными к структуре URI. Если пути пересекаются или настроены неаккуратно, возникает риск неправильного попадания запроса в сервис.

## 4. Механизм mTLS и источник сертификатов

### 4.1. Общая идея mTLS

mTLS (`mutual TLS`) представляет собой двустороннюю TLS-аутентификацию. В обычном TLS, как правило, только клиент проверяет сертификат сервера. В mTLS обе стороны проверяют идентичность друг друга. Для service mesh это критично, поскольку важно не только шифровать трафик, но и точно понимать, какой сервис обращается к какому.

### 4.2. Кто выдаёт сертификаты

В Istio центральным компонентом управления является `istiod`. Помимо других функций control plane, он выполняет роль центра сертификации (`CA`) для workload внутри mesh. Sidecar Envoy при старте связывается с `istiod` и получает:

1. сертификат;
2. приватный ключ;
3. корневой сертификат для проверки доверенной цепочки.

Эти сертификаты не прописываются вручную в приложении и не монтируются пользователем как статические файлы. Их выдача и ротация происходят автоматически средствами Istio.

### 4.3. Идентичность workload

Каждый workload в mesh получает собственную идентичность в формате SPIFFE. Она выглядит примерно так:

`spiffe://cluster.local/ns/cryptotax/sa/default`

Из этой записи видно:

1. trust domain (`cluster.local`);
2. namespace (`cryptotax`);
3. service account (`default`).

Именно эта идентичность затем может использоваться в политиках доступа, например в `AuthorizationPolicy`.

### 4.4. Как происходит само соединение

Когда одно приложение внутри Pod инициирует запрос к другому сервису, реальный сетевой вызов выполняет не само приложение, а клиентский Envoy sidecar. Он:

1. получает правило маршрутизации;
2. видит, что для данного destination установлен `ISTIO_MUTUAL`;
3. инициирует mTLS-соединение к sidecar принимающей стороны;
4. в процессе TLS-рукопожатия предъявляет свой сертификат;
5. проверяет сертификат сервера;
6. после успешной взаимной проверки передаёт HTTP/gRPC запрос дальше.

На стороне получателя входящий sidecar также проверяет сертификат клиента и только после этого пропускает трафик к контейнеру приложения. Именно поэтому plain-text запрос из Pod без sidecar не проходит при `STRICT`: у него нет mesh-сертификата, и он не может участвовать в mTLS-рукопожатии.

### 4.5. Почему приложение при этом может работать без собственного TLS

Это особенно важно для понимания. Внутри кода приложений у нас действительно могут использоваться `grpc/insecure` или обычные HTTP endpoint без встроенного TLS. Это не противоречит Istio. Шифрование и взаимная аутентификация происходят не на уровне кода приложения, а на уровне sidecar-прокси.

Именно поэтому приложение не обязано:

1. хранить сертификаты;
2. самостоятельно проверять сертификаты соседей;
3. реализовывать TLS-настройку для intra-cluster трафика.

Эта обязанность полностью вынесена в service mesh.

## 5. CORS: назначение и механизм

### 5.1. Что такое CORS

CORS (`Cross-Origin Resource Sharing`) — это браузерный механизм безопасности, который ограничивает возможность web-приложения обращаться к API, расположенным на другом origin. Под origin понимается комбинация схемы, хоста и порта. Например:

1. frontend: `http://localhost:5173`
2. backend ingress: `http://localhost:8080`

Поскольку origin различаются, браузер рассматривает такой запрос как cross-origin и применяет правила CORS.

### 5.2. Почему проблема проявлялась именно во frontend

Важно отметить, что CORS — это не общий сетевой протокол и не Kubernetes-особенность, а именно браузерное ограничение. Если тот же самый запрос отправить через `curl`, он может успешно пройти даже при полном отсутствии CORS-конфигурации. Однако браузер перед отправкой «непростого» запроса сначала выполняет preflight-запрос методом `OPTIONS`. Если сервер не отвечает корректно, основной запрос даже не будет отправлен.

Именно это и проявлялось в виде ошибки `Failed to fetch` на страницах frontend: URL могли быть синтаксически правильными, но preflight-запрос завершался некорректно.

### 5.3. Что такое preflight-запрос

Перед запросом с нестандартными заголовками, токеном авторизации, `PUT`, `PATCH`, `DELETE` или `Content-Type: application/json` браузер отправляет предварительный `OPTIONS` запрос. В нём указываются:

1. `Origin`
2. `Access-Control-Request-Method`
3. `Access-Control-Request-Headers`

Сервер должен ответить заголовками:

1. `Access-Control-Allow-Origin`
2. `Access-Control-Allow-Methods`
3. `Access-Control-Allow-Headers`
4. при необходимости `Access-Control-Max-Age`

Если этого не происходит, браузер блокирует дальнейший вызов.

### 5.4. Как CORS реализован у нас

Вместо того чтобы настраивать CORS отдельно в каждом сервисе, он был вынесен на уровень Istio ingress через `corsPolicy` в `VirtualService`. Это означает, что обработка preflight происходит уже на входном прокси, до передачи запроса в backend. Такой подход удобен, поскольку позволяет централизованно задавать одинаковые правила для всей frontend-схемы.

В нашей конфигурации разрешены:

1. origins вида `http://localhost:*` и `http://127.0.0.1:*`;
2. методы `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`;
3. заголовки `Authorization`, `Content-Type`, `Accept`.

За счёт этого frontend на Vite dev-server может корректно обращаться к ingress на `8080`, а preflight-запросы больше не приводят к сетевым ошибкам в браузере.

## 6. AuthorizationPolicy: контроль доступа внутри mesh

### 6.1. Место в общей схеме

Если `PeerAuthentication` отвечает на вопрос, какой тип транспортного соединения разрешён, то `AuthorizationPolicy` отвечает на вопрос, кому вообще можно выполнять запрос после успешного установления соединения.

Можно сформулировать так:

1. mTLS подтверждает техническую идентичность участника.
2. `AuthorizationPolicy` решает, имеет ли этот участник право доступа.

### 6.2. Семантика ALLOW и DENY

`AuthorizationPolicy` может содержать правила типа `ALLOW` и `DENY`. Семантически это означает следующее:

1. `DENY` используется для явного запрета.
2. `ALLOW` используется для формирования списка допустимых вызовов.

Если для workload существует хотя бы одна политика `ALLOW`, то любые запросы, не попавшие под её правила, считаются запрещёнными. Следовательно, наличие `ALLOW` уже само по себе сужает поверхность доступа.

### 6.3. Что именно фильтруется

Политика может учитывать:

1. namespace источника;
2. principal источника;
3. service account;
4. путь HTTP;
5. метод HTTP;
6. порт;
7. IP-адрес и другие признаки.

Таким образом, `AuthorizationPolicy` может быть как грубой, так и очень точной. Например, можно разрешить всем workload из namespace `cryptotax` доступ к `tax-svc` по определённому порту. А можно разрешить только `aggregation-svc` с конкретным service account доступ только к определённому URI.

### 6.4. Как это реализовано в текущем проекте

В текущей dev-конфигурации реализован базовый вариант. Для каждого сервиса задана `ALLOW` политика, разрешающая доступ:

1. из namespace `istio-system` — это нужно для ingressgateway;
2. из namespace `cryptotax` — это нужно для внутренних вызовов сервисов друг к другу.

Также дополнительно ограничены порты, на которые разрешён входящий трафик. Это означает, что даже внутри mesh вызовы становятся более предсказуемыми: сервис принимает только ожидаемый трафик через известные точки входа.

### 6.5. Направления дальнейшего усиления

Текущая схема достаточна для MVP и учебного окружения, но в production-подходе её обычно усиливают:

1. вместо namespace-based доступа используют `source.principals`;
2. вводят разделение прав по конкретным service accounts;
3. добавляют правила на уровне методов и путей;
4. формируют комбинации `DENY` и `ALLOW` для критичных API.

Именно это позволяет переходить от «доступ разрешён сервисам данного namespace» к модели «доступ разрешён только конкретному вызывающему сервису при обращении к конкретному endpoint».

## 7. Как все компоненты работают совместно

После настройки Istio полная цепочка обработки запроса выглядит следующим образом:

1. frontend или внешний клиент отправляет запрос на единый ingress-адрес, например `http://localhost:8080`;
2. трафик попадает в `istio-ingressgateway`;
3. `Gateway` определяет, что данный входной трафик вообще должен приниматься;
4. `RequestAuthentication` проверяет JWT по `issuer`, `audience` и JWKS, а затем при необходимости копирует claims в headers;
5. `AuthorizationPolicy` на ingress решает, разрешён ли сам входящий запрос с учётом статуса аутентификации и маршрута;
6. `VirtualService` анализирует путь и выбирает целевой backend-сервис;
7. клиентский Envoy использует `DestinationRule` и устанавливает mTLS-соединение;
8. принимающая сторона проверяет через `PeerAuthentication`, допустим ли тип соединения;
9. затем backend `AuthorizationPolicy` решает, допустим ли вызов с точки зрения источника и наличия требуемых headers;
10. только после успешного прохождения всех этих уровней трафик доходит до контейнера приложения.

В итоге Istio образует самостоятельный сетевой слой, который делает поведение системы более управляемым и предсказуемым. Приложения остаются сосредоточены на бизнес-логике, в то время как маршрутизация, шифрование, контроль доступа и обработка browser-specific сетевых требований выносятся в инфраструктуру кластера.
