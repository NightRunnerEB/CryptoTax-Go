**2 ТЕКСТ ПРОГРАММЫ**

Полный текст программы расположен в двух репозиториях проекта CryptoTax: `NightRunnerEB/CryptoTax-Go` [1] и `NightRunnerEB/CryptoTax` [2]. Такое разделение связано с выбранной гетерогенной архитектурой: часть сервисов реализована на языке Go, а часть — на языке Rust. Исходные тексты сгруппированы по сервисам и общим пакетам, что позволяет независимо развивать компоненты системы и переиспользовать инфраструктурный код.

В репозитории `CryptoTax-Go` расположены общие контракты и основная часть backend-инфраструктуры. В корне репозитория находятся директории `api` с proto-описаниями gRPC-контрактов, `gen` со сгенерированным кодом, `pkg` с общими пакетами, `services` с исходными текстами сервисов, `docs` с архитектурной и API-документацией, `frontend` с веб-интерфейсом, а также `docker-compose.yml` для локального запуска системы. В репозитории `CryptoTax` расположены сервисы `auth-svc` и `ledger-svc`, реализованные на языке Rust.

Внешний доступ к системе организован через HTTP API. Для пользовательских сценариев используются REST-маршруты, документированные в OpenAPI-спецификациях, а для внутренних высоконагруженных вызовов между сервисами используются gRPC и Protocol Buffers [3], [4]. Долгие и потенциально отказоустойчивые этапы обработки, такие как импорт и агрегация данных, вынесены в асинхронный контур с использованием RabbitMQ [5].

**2.1 Общие пакеты и структура сервисов**

Общие Go-пакеты расположены в директории `pkg` репозитория `CryptoTax-Go`. Они используются несколькими сервисами и обеспечивают единообразную работу с инфраструктурой и служебными механизмами. В проекте выделены следующие общие пакеты:

- `pkg/logger` — пакет структурированного логирования на базе `zap`;
- `pkg/postgres` — пакет подключения к PostgreSQL [6] и настройки пула соединений;
- `pkg/redis` — пакет подключения к Redis [7];
- `pkg/minio` — пакет работы с S3-совместимым объектным хранилищем MinIO [8];
- `pkg/telemetry` — пакет инициализации OpenTelemetry [9];
- `pkg/in-memory` — набор in-memory реализаций для справочных и вспомогательных сценариев.

Каждый Go-сервис имеет схожую внутреннюю структуру. В директории `cmd` расположена точка входа в сервис. Директория `internal` содержит основную реализацию и, как правило, делится на следующие части:

- `app` — сборка зависимостей, инициализация конфигурации, запуск серверов и фоновых процессов;
- `config` — описание структуры конфигурации и её загрузка из YAML и переменных окружения;
- `domain` — доменные сущности, значения, интерфейсы портов и доменные ошибки;
- `usecases` — прикладные сценарии использования и оркестрация доменной логики;
- `infra` или `internal/infra` — реализации репозиториев, клиентов внешних сервисов, lock-менеджеров и других инфраструктурных компонентов;
- `server` — реализация gRPC-обработчиков и интеграция с `grpc-gateway`;
- `worker` — фоновые обработчики очередей и периодические воркеры.

В директории `db` располагаются SQL-миграции и SQL-запросы для `sqlc`. Такой подход позволяет хранить SQL в явном виде и получать типобезопасный код доступа к данным на этапе генерации.

**2.2 Сервис аутентификации (`auth-svc`)**

Сервис `auth-svc` расположен в репозитории `CryptoTax` и реализован на языке Rust [10]. Он отвечает за регистрацию пользователей, вход, обновление токенов доступа, завершение сессии и подтверждение адреса электронной почты.

Исходный код сервиса расположен в директории `auth-svc/src`. Внутри выделены слои маршрутов, доменной логики, репозиториев и инфраструктуры базы данных. Сервис предоставляет REST API для пользовательских операций аутентификации и выступает источником данных о пользователе и tenant-контексте.

При обращении пользователя к защищённым маршрутам `auth-svc` участвует в схеме доступа через выпуск и проверку JWT. Полученный идентификатор пользователя и идентификатор tenant далее используются другими сервисами для изоляции данных и выполнения операций только в пределах соответствующего аккаунта.

**2.3 Сервис импорта и нормализации транзакций (`ledger-svc`)**

Сервис `ledger-svc` расположен в репозитории `CryptoTax` и также реализован на языке Rust. Он отвечает за приём CSV-файлов из внешних источников, валидацию строк, нормализацию операций и сохранение результата импорта.

В составе сервиса выделены:

- маршруты HTTP для загрузки файлов и получения результатов импорта;
- парсеры, специфичные для поддерживаемых бирж и форматов выгрузок;
- доменные структуры нормализованной транзакции;
- слой доступа к PostgreSQL для хранения импортов и транзакций.

`ledger-svc` преобразует разнородные CSV-форматы к единой внутренней модели транзакции. На этом этапе определяются основные поля операции: время, источник, тип действия, входящий актив, исходящий актив, комиссия и вспомогательные метаданные. Дополнительно сервис выполняет валидацию обязательных полей и отклоняет некорректные строки с формированием детализированной информации об ошибках.

После завершения успешного импорта сервис публикует событие, по которому downstream-компоненты могут начать дальнейшую обработку данных. Кроме того, `ledger-svc` предоставляет внутренний API для выдачи списка транзакций по конкретному импорту и API для получения списка поддерживаемых бирж.

**2.4 Сервис исторического прайсинга (`price-svc`)**

Сервис `price-svc` расположен в директории `services/price-svc` репозитория `CryptoTax-Go`. Он реализован на языке Go и предназначен для стоимостной оценки криптовалютных операций в выбранной фиатной валюте.

Сервис получает запросы по gRPC, разрешает тикеры активов в канонические идентификаторы внешнего источника цен, запрашивает исторические котировки и выполняет пересчёт в целевую фиатную валюту. Для хранения исторических данных используется PostgreSQL, для ускорения повторных вычислений — Redis. Поддерживается работа с криптовалютными котировками в USD и их последующая конвертация в локальные фиатные валюты через отдельный слой FX-провайдеров.

Внутри `price-svc` выделены следующие основные подсистемы:

- `internal/server` — gRPC-сервер и обработчики запросов;
- `internal/usecases` — прикладная логика оценки исторических цен;
- `internal/coingecko` — интеграция с внешним провайдером рыночных котировок;
- `internal/fiatfx` — модуль получения курсов фиатных валют;
- `internal/infra` — доступ к базе данных, кэшу и внутренним справочникам.

Сервис проектируется как отдельный вычислительный контур, поскольку прайсинг зависит от внешних провайдеров, подвержен ограничениям по частоте запросов и требует кэширования и повторного использования ранее рассчитанных значений.

**2.5 Сервис агрегации и read-model (`aggregation-svc`)**

Сервис `aggregation-svc` расположен в директории `services/aggregation-svc` репозитория `CryptoTax-Go`. Он принимает нормализованные транзакции после импорта, запрашивает для них стоимостную оценку у `price-svc`, сохраняет обогащённые данные и предоставляет read-model для пользовательских запросов.

Основные задачи сервиса:

- потребление события о завершении импорта;
- загрузка нормализованных транзакций из `ledger-svc`;
- батч-запрос стоимости операций в `price-svc`;
- сохранение агрегированных транзакций в собственной базе;
- предоставление API для списков транзакций, tenant-настроек и справочника поддерживаемых фиатных валют.

В доменной модели `aggregation-svc` каждая агрегированная транзакция хранит не только исходные данные операции, но и результат стоимостной оценки: входящие, исходящие и комиссионные legs с криптовалютным количеством, фиатной стоимостью и возможной диагностикой. Это делает сервис промежуточным, но критически важным слоем между импортом сырой истории операций и последующим налоговым расчётом.

Пользовательские настройки tenant, такие как целевая фиатная валюта и временная зона, также хранятся в `aggregation-svc`, поскольку именно этот сервис отвечает за представление транзакций в согласованном виде для пользовательского интерфейса и downstream-сервисов.

**2.6 Сервис налогового расчёта (`tax-svc`)**

Сервис `tax-svc` расположен в директории `services/tax-svc` репозитория `CryptoTax-Go`. Он реализует прикладную логику налогового расчёта, управление профилем налогоплательщика, создание и обработку заданий на расчёт, а также формирование итогового audit-результата.

Внешний REST API сервиса публикуется через `grpc-gateway`. Сервис предоставляет методы для:

- получения и обновления профиля налогоплательщика;
- запуска нового расчёта за налоговый период;
- получения статуса задания;
- получения списка ранее созданных заданий.

После создания задания `tax-svc` переводит его в очередь на обработку. Фоновый воркер сервиса атомарно забирает задание, запрашивает готовые агрегированные транзакции через gRPC у `aggregation-svc`, выбирает движок расчёта в зависимости от налоговой политики и юрисдикции, а затем формирует результат расчёта. Результат включает события учёта, лоты, строки списания, итоговую налоговую сводку и audit-артефакты.

Для поддержки расширяемости в сервисе выделен слой `engines`: каждая юрисдикция оформляется как отдельный движок расчёта с единым интерфейсом. Это позволяет изолировать правила классификации операций, расчёта лотов и формирования итоговой налоговой базы по странам.

Дополнительно `tax-svc` интегрирован с объектным хранилищем MinIO. В нём сохраняются audit-артефакты и иные файлы, а в базе данных хранятся только стабильные object keys. В момент запроса статуса задания сервис может сформировать новый временный presigned URL для скачивания соответствующего артефакта.

**2.7 Сервис формирования отчётных документов (`report-svc`)**

Сервис `report-svc` расположен в директории `services/report-svc` репозитория `CryptoTax-Go`. Он выделен как отдельный сервис формирования отчётных документов на основе уже подготовленного результата расчёта.

Архитектурно `report-svc` отвечает за преобразование расчётной модели в формальный отчётный артефакт. В текущем целевом варианте сервис принимает структурированный результат из `tax-svc`, формирует итоговый XML-документ, сохраняет его в объектное хранилище и возвращает object key, который далее используется `tax-svc` как ссылка на сформированный отчёт.

Выделение генерации отчётных файлов в отдельный сервис позволяет:

- изолировать шаблоны и форматирование отчётов от налогового движка;
- упростить расширение под новые виды документов и новые юрисдикции;
- не смешивать вычислительную бизнес-логику и файловую генерацию в одном компоненте.

**2.8 API Gateway, внешние контракты и frontend**

Внешний HTTP-контур системы строится вокруг Nginx и REST-маршрутов, публикуемых сервисами. Для Go-сервисов REST-доступ строится поверх `grpc-gateway`, что позволяет поддерживать единый gRPC-контракт внутри системы и при этом отдавать удобное HTTP API наружу.

Контракты внешнего и внутреннего API документированы в директории `docs/api` в единой OpenAPI-спецификации.

Веб-интерфейс проекта расположен в директории `frontend` и реализован на React [11] с использованием Vite [12]. Он предназначен для демонстрации и пользовательской работы со следующими сценариями:

- загрузка и просмотр импортов;
- выбор биржи и пользовательских настроек;
- просмотр агрегированных транзакций;
- запуск налогового расчёта и получение статуса задания;
- скачивание итоговых артефактов.

**2.9 Инфраструктура запуска и наблюдаемость**

Для локального запуска и отладки в проекте используется `docker-compose.yml`, в котором описан запуск инфраструктурных зависимостей и вспомогательных компонентов. В системе используются PostgreSQL, Redis, RabbitMQ, MinIO, а также стек наблюдаемости на базе OpenTelemetry, Prometheus, Loki и Grafana [9], [13], [14], [15].

Каталог `observability` содержит конфигурации коллекторов телеметрии, Prometheus и Grafana. Такой подход позволяет контролировать состояние сервисов, анализировать структурированные логи и отслеживать производительность ключевых RPC и HTTP-методов.

Таким образом, исходный текст программы CryptoTax представляет собой набор взаимосвязанных, но изолированных сервисов и общих пакетов. Каждый компонент отвечает за свой этап обработки данных: от аутентификации пользователя и загрузки транзакций до стоимостной оценки, агрегации, налогового расчёта и формирования итоговых отчётных артефактов.
