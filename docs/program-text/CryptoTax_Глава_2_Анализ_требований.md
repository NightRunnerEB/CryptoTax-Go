# Глава 2. Анализ требований

## 2.1 Основные сущности

Для проектирования системы CryptoTax необходимо формально определить ключевые сущности, с которыми работает backend. Эти сущности задают предметную модель системы и определяют, какие данные должны храниться, валидироваться, передаваться между сервисами и использоваться в расчётах.

### Пользователь и tenant

Базовой сущностью системы является пользователь, который проходит регистрацию, подтверждает адрес электронной почты, получает доступ к системе и выполняет дальнейшие операции с собственными данными. На уровне backend-контекста пользователь связан с tenant-идентификатором, который используется для изоляции данных. Все операции, связанные с импортом, агрегацией, настройками, расчётом налогов и генерацией отчётов, выполняются в рамках конкретного tenant.

Таким образом, tenant выступает единицей логической изоляции данных: один пользователь или одна организация работает только со своей историей операций, своими настройками и своими отчётными артефактами.

### Импорт

Сущность импорта описывает одну загрузку данных из внешнего источника, как правило из CSV-файла биржи или иного сервиса. Импорт хранит информацию об источнике, времени создания, статусе обработки, а также связывает набор загруженных транзакций в единый пакет.

Импорт необходим для того, чтобы:

1. группировать транзакции по факту загрузки;
2. отслеживать состояние обработки конкретного файла;
3. повторно получать данные по конкретному импорту;
4. запускать downstream-обработку после завершения загрузки.

### Нормализованная транзакция

После разбора CSV-строк данные преобразуются в нормализованную внутреннюю транзакцию. Это центральная сущность операционного контура системы. Такая транзакция содержит:

1. идентификатор;
2. user_id;
3. import_id;
4. источник данных;
5. время операции;
6. тип операции;
7. входящий, исходящий и комиссионный legs;
8. дополнительные метаданные, например `tx_hash`, `order_id`, `position_id`, `contract_symbol`, `note`.

Нормализованная транзакция нужна для того, чтобы все последующие сервисы работали не с исходными CSV-форматами бирж, а с единой моделью, одинаковой для всех источников.

### Money leg

С каждой транзакцией связаны один или несколько legs: `in_money`, `out_money`, `fee_money`. Leg описывает одну стоимостную сторону операции и содержит как минимум:

1. символ актива;
2. количество;
3. в дальнейшем — стоимостную оценку в фиате;
4. при необходимости — диагностическую информацию об ошибке оценки.

Использование leg-модели позволяет единообразно описывать сделки, переводы, комиссии, доходы и иные типы действий, не жёстко завязываясь на формат конкретной биржи.

### AggregatedTransaction

После прохождения через сервис агрегации нормализованная транзакция превращается в агрегированную транзакцию. Эта сущность сохраняет исходный смысл операции, но дополняется результатом стоимостной оценки: для каждого leg появляется рассчитанная фиатная стоимость. Именно эта сущность является источником данных для пользовательского просмотра операций и для последующего налогового расчёта.

Смысл выделения `AggregatedTransaction` в отдельную сущность заключается в разделении сырых нормализованных данных и подготовленного read-model представления. Это позволяет отделить импорт от отображения и расчёта, а также переоценивать данные в другой фиатной валюте без изменения исходного сохранённого состояния.

### TenantSettings

Для каждого tenant в системе существуют настройки агрегации. На текущем этапе ключевыми параметрами являются:

1. целевая фиатная валюта для read-model;
2. временная зона.

Эти настройки используются сервисом агрегации для подготовки пользовательского представления операций. При этом они не обязаны совпадать с валютой итогового налогового расчёта: налоговый контур может запросить те же операции в другой валюте, соответствующей конкретной юрисдикции.

### TaxProfile

Сущность `TaxProfile` описывает сведения о налогоплательщике и параметры, необходимые для расчётного контура. В текущей модели профиль включает:

1. ИНН;
2. фамилию, имя, отчество;
3. временную зону;
4. телефон;
5. список собственных кошельков;
6. налоговый статус резидентства;
7. тип налогоплательщика.

Профиль хранится в `tax-svc` и используется при создании и выполнении расчётных заданий. Его наличие является обязательным условием для запуска налогового расчёта.

### TaxPolicy

Помимо профиля, важной сущностью является `TaxPolicy` — снимок правил, используемых для конкретного запуска расчёта. В него входят параметры вроде юрисдикции, метода cost basis и политики обработки отдельных типов операций.

Разделение `TaxProfile` и `TaxPolicy` позволяет не смешивать персональные данные налогоплательщика с параметрами конкретного запуска расчёта. Это важно для воспроизводимости: один и тот же набор транзакций может быть рассчитан по разным правилам, и система должна явно фиксировать, какие именно правила были использованы.

### TaxJob

`TaxJob` является сущностью фонового выполнения расчёта. Она содержит:

1. идентификатор задания;
2. user_id;
3. налоговый год;
4. policy snapshot;
5. статус выполнения;
6. количество попыток обработки;
7. временные отметки создания, старта и завершения;
8. итоговую сводку расчёта;
9. object keys audit- и report-артефактов;
10. сведения об ошибке.

Через `TaxJob` реализуется жизненный цикл расчёта: постановка в очередь, атомарный захват воркером, повторные попытки при временных сбоях, сохранение результата и выдача статуса клиенту.

### TaxSummary

Итоговым кратким результатом расчёта является `TaxSummary`, включающая:

1. общий доход;
2. общий расход;
3. налоговую базу;
4. рассчитанный налог.

Эта сущность используется для быстрого просмотра результата расчёта без необходимости каждый раз анализировать полный audit-артефакт.

### Отчётный артефакт

Отдельной сущностью на уровне системы является отчётный артефакт — файл, сформированный на основе результата расчёта и сохранённый в объектном хранилище. Сервис `tax-svc` хранит только стабильный `object_key` такого артефакта, а временная ссылка на скачивание формируется динамически при запросе статуса.

Таким образом, основные сущности CryptoTax покрывают весь сквозной путь данных: от пользователя и импорта до агрегированной операции, налогового профиля, задания на расчёт, итоговой сводки и файлового артефакта. Именно на основе этих сущностей в работе целесообразно приводить основные доменные модели и схемы: схему импорта транзакций, схему агрегированной операции, схему налогового профиля, схему расчётного задания и схему формирования итогового отчётного артефакта.

## 2.2 Функциональные требования

На основе анализа предметной области и предполагаемого сценария использования можно сформулировать основные функциональные требования к системе CryptoTax.

### Требования к аутентификации и доступу

Система должна обеспечивать:

1. регистрацию нового пользователя;
2. подтверждение адреса электронной почты;
3. вход пользователя в систему;
4. обновление токенов доступа;
5. завершение пользовательской сессии;
6. передачу и использование tenant-контекста во всех защищённых сценариях.

### Требования к импорту и нормализации данных

Система должна обеспечивать:

1. выдачу списка поддерживаемых бирж и форматов импорта;
2. загрузку CSV-файлов транзакций;
3. проверку структуры и формата входных файлов;
4. преобразование строк CSV в единую внутреннюю модель транзакции;
5. сохранение результата импорта;
6. получение списка транзакций по конкретному импорту.

### Требования к стоимостной оценке операций

Система должна обеспечивать:

1. получение исторических котировок активов;
2. пакетную стоимостную оценку транзакций;
3. поддержку нескольких фиатных валют;
4. tenant-specific сопоставление неоднозначных символов активов;
5. хранение и повторное использование ранее полученных цен.

### Требования к агрегации и read-model

Система должна обеспечивать:

1. получение транзакций после завершения импорта;
2. запуск стоимостной оценки этих транзакций;
3. сохранение агрегированных транзакций в собственной read-model;
4. выдачу агрегированных транзакций по импорту;
5. выдачу агрегированных транзакций по диапазону времени;
6. хранение tenant-настроек агрегации;
7. выдачу списка поддерживаемых фиатных валют;
8. временную переоценку read-model в другую валюту без изменения сохранённого состояния.

### Требования к налоговому расчёту

Система должна обеспечивать:

1. хранение и изменение налогового профиля;
2. валидацию налогового профиля;
3. создание задания на расчёт;
4. атомарный захват задания фоновым воркером;
5. повторные попытки выполнения при временных сбоях зависимостей;
6. получение агрегированных транзакций за нужный налоговый период;
7. выбор расчётного движка в зависимости от налоговой политики;
8. формирование промежуточного расчётного результата: событий, лотов и итоговой сводки;
9. сохранение audit-артефакта;
10. выдачу статуса задания;
11. выдачу списка заданий.

### Требования к формированию отчёта

Система должна обеспечивать:

1. передачу подготовленного результата расчёта в сервис генерации отчёта;
2. формирование итогового отчётного документа;
3. сохранение отчёта в объектном хранилище;
4. возврат object key сформированного документа в расчётный контур.

### Требования к наблюдаемости и устойчивости

Система должна обеспечивать:

1. структурированное логирование;
2. сбор технических метрик;
3. наличие health-check интерфейсов;
4. корректную обработку ошибок ввода и ошибок внешних зависимостей;
5. воспроизводимость выполнения фоновых расчётных сценариев.

Таким образом, функциональные требования покрывают как пользовательские операции, так и внутренний системный pipeline обработки данных.

## 2.3 Требования к интерфейсу

В рамках данной работы специальные требования к пользовательскому интерфейсу не предъявляются. Пользовательский интерфейс рассматривается как демонстрационный слой, предназначенный для проверки работоспособности backend-системы и демонстрации основных сценариев использования.

Следовательно, в данной главе не формулируются отдельные требования к визуальному оформлению, адаптивности, композиции экранов и иным аспектам полнофункционального UI. Основное внимание уделяется серверной части системы, корректности обработки данных и реализуемым прикладным сценариям.

## 2.4 Сценарии использования

Чтобы зафиксировать прикладной смысл требований, целесообразно описать несколько ключевых сценариев использования системы.

### Сценарий 1. Регистрация пользователя

1. Пользователь отправляет регистрационные данные.
2. `auth-svc` валидирует email и пароль.
3. Создаётся пользовательская запись.
4. Инициализируется связанный downstream-контур профиля.
5. Пользователь получает письмо для подтверждения email.

Результат сценария: в системе появляется новый пользователь, готовый к дальнейшей работе после подтверждения email.

### Сценарий 2. Загрузка истории транзакций

1. Пользователь выбирает поддерживаемую биржу.
2. Отправляет CSV-файл в `ledger-svc`.
3. Сервис проверяет структуру файла, валидирует строки и нормализует операции.
4. Создаётся import и сохраняются нормализованные транзакции.

Результат сценария: в системе появляется новый импорт и связанный с ним набор транзакций.

### Сценарий 3. Формирование read-model операций

1. После завершения импорта downstream-контур получает сигнал о новом наборе транзакций.
2. `aggregation-svc` запрашивает транзакции у `ledger-svc`.
3. `price-svc` выполняет их стоимостную оценку.
4. `aggregation-svc` сохраняет агрегированные транзакции и делает их доступными для чтения.

Результат сценария: пользователь и downstream-сервисы получают доступ к read-model операций с рассчитанными фиатными значениями.

### Сценарий 4. Настройка параметров tenant

1. Пользователь или оператор получает текущие настройки tenant.
2. Изменяет целевую валюту и/или временную зону.
3. Сервис валидирует новые значения и сохраняет их.

Результат сценария: read-model выдаётся с учётом актуальных пользовательских настроек.

### Сценарий 5. Настройка налогового профиля

1. Пользователь заполняет налоговый профиль.
2. `tax-svc` проверяет обязательные поля и корректность значений.
3. Профиль сохраняется и становится доступным для последующих расчётов.

Результат сценария: появляется валидный налоговый профиль, необходимый для запуска расчёта.

### Сценарий 6. Запуск налогового расчёта

1. Пользователь указывает налоговый год и политику расчёта.
2. `tax-svc` создаёт новое задание `TaxJob` со статусом `queued`.
3. Фоновый воркер атомарно забирает это задание.
4. Загружаются агрегированные транзакции за нужный период.
5. Выбирается расчётный движок и выполняется построение результата.
6. Формируется итоговая сводка и audit-артефакт.

Результат сценария: задание либо завершается успешно и содержит результат расчёта, либо переводится в ошибочное состояние / повторную попытку.

### Сценарий 7. Получение результата расчёта

1. Пользователь или внешний клиент запрашивает статус задания.
2. `tax-svc` возвращает текущий статус, summary и информацию об ошибке, если она есть.
3. Если доступны object keys артефактов, сервис формирует presigned URL.

Результат сценария: пользователь получает не только признак завершённости расчёта, но и доступ к связанным артефактам.

### Сценарий 8. Генерация итогового отчётного документа

1. После завершения расчёта `tax-svc` передаёт подготовленный результат в `report-svc`.
2. `report-svc` формирует итоговый отчётный документ.
3. Документ сохраняется в объектном хранилище.
4. В расчётный контур возвращается object key отчётного артефакта.

Результат сценария: система формирует итоговый документ, пригодный для дальнейшего использования и скачивания.

Были определены ключевые сущности, которые участвуют в обработке данных, сформулированы функциональные требования к основным подсистемам, зафиксированы требования к программному интерфейсу и описаны основные сценарии использования.

Такое представление позволяет отделить уровень требований и доменной модели от архитектурных и технологических решений. На его основе можно перейти к следующей главе, посвящённой уже не тому, *что* должна делать система, а тому, *как* именно организована её архитектура и каким образом выбранные сервисы, хранилища и контракты реализуют сформулированные требования.
