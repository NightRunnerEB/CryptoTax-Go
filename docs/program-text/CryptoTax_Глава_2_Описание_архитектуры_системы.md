## 2.2 Описание архитектуры системы

Исходя из требований к системе CryptoTax, а именно необходимости принимать транзакции из разнородных внешних источников, нормализовать их, выполнять историческую стоимостную оценку, формировать агрегированные представления данных, рассчитывать налоговые показатели и подготавливать итоговые отчётные артефакты, в качестве целевой была выбрана микросервисная архитектура. Такой подход позволяет разделить ответственность между компонентами системы и изолировать наиболее сложные этапы обработки данных: импорт, прайсинг, агрегацию, налоговый расчёт и генерацию отчёта.

Каждый сервис разворачивается как самостоятельный процесс и отвечает за ограниченную предметную область. Для большинства backend-компонентов используется принцип `database-per-service`, при котором каждый сервис владеет своей схемой данных и не обращается напрямую к таблицам других сервисов. Это уменьшает связность между компонентами, упрощает эволюцию внутренней модели данных и позволяет независимо развивать отдельные части системы.

Внешний контур доступа организован через API Gateway на базе Nginx. Именно gateway является единой точкой входа для внешних клиентов и маршрутизирует запросы к соответствующим сервисам. Для пользовательских сценариев внешний интерфейс системы представлен REST API. В Go-сервисах этот REST-контур публикуется через `grpc-gateway`, что позволяет использовать единый gRPC-контракт внутри системы и одновременно предоставлять HTTP API без дублирования прикладной логики. Сервисы, реализованные на Rust, публикуют REST endpoints напрямую.

Проверка JWT-токенов выполняется на входном gateway-слое. После успешной проверки в downstream-сервисы передаются доверенные заголовки с контекстом пользователя и tenant, в частности `X-User-Id`, `X-User-Id` и при необходимости `X-Roles`. Благодаря этому внутренние сервисы не дублируют полный цикл аутентификации и не реализуют повторную проверку токена, а используют уже проверенный контекст для tenant-изоляции данных и контроля доступа на прикладном уровне.

С точки зрения межсервисного взаимодействия в системе используется гибридная модель. Синхронные вызовы применяются в тех сценариях, где необходим немедленный ответ и строгий контракт между компонентами. Для этого используются REST и gRPC, причём gRPC выступает основным механизмом внутренних вызовов между Go-сервисами. Асинхронное взаимодействие применяется только там, где оно действительно оправдано архитектурой и характером нагрузки, например в обработке завершённого импорта и обновлении read-model. Для таких сценариев используется RabbitMQ, позволяющий запускать downstream-обработку без блокировки пользовательского запроса.

Для хранения данных используется несколько специализированных уровней. PostgreSQL выступает основным транзакционным хранилищем для сервисных данных, Redis применяется как кэш и вспомогательное техническое хранилище, а объектное хранилище MinIO используется для сохранения файловых артефактов, например audit-результатов расчёта и итоговых отчётных документов. При этом в базах данных сервисов сохраняются стабильные object keys, а временные ссылки на скачивание формируются только на этапе чтения результата.

Отдельное значение в архитектуре имеет контур наблюдаемости. Для сервисов настраиваются структурированные логи, health-check интерфейсы и экспорт метрик через OpenTelemetry. Это необходимо не только для эксплуатации системы, но и для отладки сложных интеграционных сценариев, в которых участвуют несколько сервисов, внешние провайдеры данных и асинхронные фоновые процессы.

Таким образом, архитектура CryptoTax представляет собой набор изолированных, но согласованно взаимодействующих сервисов, объединённых общим API-контуром, единым tenant-контекстом и специализированной инфраструктурой хранения, обмена сообщениями и наблюдаемости. Такое построение позволяет поэтапно развивать систему, не смешивая в одном компоненте импорт данных, вычислительную логику, read-model и генерацию итоговых документов.
