Глава 3. Программная реализация системы

3.1 Общая организация исходного кода и репозиториев

Программная реализация CryptoTax построена как набор backend-сервисов, разделённых по предметным областям и техническим задачам. На практике система распределена по двум связанным репозиториям.

Первый репозиторий, `CryptoTax-Go`, содержит общие контракты и основную часть инфраструктурных сервисов, реализованных на языке Go. В нём расположены директории `api` с proto-описаниями gRPC-интерфейсов, `gen` со сгенерированным кодом, `pkg` с переиспользуемыми пакетами, `services` с исходными текстами сервисов, `docs` с API- и архитектурной документацией, а также `frontend`, используемый как отдельный web-клиент проекта. Внутри `services` на текущем этапе реализованы `price-svc`, `aggregation-svc`, `tax-svc` и `report-svc`.

Второй репозиторий, `CryptoTax`, содержит сервисы `auth-svc` и `ledger-svc`, реализованные на языке Rust. Такое разделение обусловлено выбранным гетерогенным стеком: сервисы, в которых особенно важны строгая обработка входных данных, производительность и надёжная работа с файловым импортом, были реализованы на Rust, тогда как большая часть интеграционных и расчётных компонентов — на Go.

Для всех Go-сервисов используется схожая внутренняя структура. В директории `cmd` располагается точка входа, `internal/domain` содержит доменные модели, значения и интерфейсы портов, `internal/usecases` — прикладные сценарии использования, `internal/infra` — инфраструктурные реализации репозиториев и клиентов, `internal/server` — gRPC- и grpc-gateway-слой, `db` — SQL-миграции и SQL-запросы для `sqlc`. Такой подход позволяет отделить прикладную логику от деталей сетевого и хранилищного взаимодействия и поддерживать единообразие кода между сервисами.

Отдельную роль играют общие пакеты в директории `pkg`. В частности, `pkg/logger` используется для структурированного логирования, `pkg/postgres` и `pkg/redis` — для унифицированного подключения к инфраструктурным зависимостям, `pkg/minio` — для работы с объектным хранилищем, а `pkg/telemetry` — для инициализации OpenTelemetry и стандартного контура наблюдаемости.

3.2 Реализация сервиса аутентификации

Сервис `auth-svc` реализован на Rust с использованием `axum`, `sqlx`, `redis`, `lettre`, `jsonwebtoken` и `argon2`. Он предоставляет REST API для регистрации, входа, обновления токенов, завершения сессии и подтверждения адреса электронной почты. Маршруты сервиса формируются в отдельном модуле и включают `POST /auth/register`, `POST /auth/login`, `POST /auth/refresh`, `POST /auth/logout`, `GET /auth/verify` и `GET /health`.

С практической точки зрения важной особенностью реализации является то, что `auth-svc` отвечает не только за выпуск и ротацию токенов, но и за инициализацию минимального налогового профиля пользователя. При регистрации пользователя сервис выполняет синхронный запрос в `tax-svc` для создания начального профиля. Если этот шаг завершается неуспешно, выполняется компенсирующее удаление только что созданного пользователя. Такое решение позволяет не оставлять систему в промежуточном состоянии, когда пользователь уже зарегистрирован, а downstream-профиль для налогового контура ещё не создан.

Пароли хранятся в захешированном виде с использованием `argon2`, а короткоживущие access token и долгоживущие refresh token управляются раздельно. Для подтверждения электронной почты используется одноразовый токен с ограниченным сроком жизни. Валидация входных данных выполняется на уровне use case: нормализуется email, проверяется сложность пароля, корректность refresh token и статус пользователя.

Сервис предоставляет отдельный health endpoint, а также поддерживает CORS-настройки для локального frontend-окружения. При этом в общей архитектуре системы аутентификация и проверка JWT вынесены на входной контур, а tenant- и user-контекст затем передаётся остальным сервисам через заголовки.

3.3 Реализация сервиса импорта и нормализации транзакций

Сервис `ledger-svc` реализован на Rust и отвечает за приём CSV-файлов, парсинг строк, нормализацию операций и сохранение результата импорта. Он также предоставляет внутренний REST endpoint для получения списка транзакций по конкретному импорту и endpoint для выдачи списка поддерживаемых бирж.

Архитектурно сервис использует реестр биржевых обработчиков. В момент запуска формируется `ExchangeRegistry`, в который регистрируются конкретные реализации, например для MEXC и OKX. Благодаря этому добавление нового формата импорта не требует изменения уже существующих обработчиков и сводится к подключению нового сервиса парсинга и его регистрации в реестре.

На этапе импорта `ledger-svc` получает multipart-запрос с CSV-файлом, определяет требуемый обработчик, построчно считывает содержимое и преобразует записи в единую внутреннюю модель транзакции. На этом же этапе выполняется валидация структуры файла, обязательных колонок, числовых полей, времени операции и допустимых типов действий. Для downstream-сервисов это критично: агрегация и расчёт строятся уже не на сыром CSV, а на унифицированной модели, в которой операция представлена в одинаковом виде независимо от конкретной биржи.

Помимо основного import endpoint, сервис реализует `GET /v1/exchanges/supported`, что позволяет внешнему контуру строить интерфейс выбора биржи на основе фактически поддерживаемых обработчиков, и `GET /v1/imports/{import_id}/transactions` (с user id из header `X-User-Id`), который используется другими сервисами для получения уже нормализованной истории операций по импорту.

Отдельный интерес представляет то, что `ledger-svc` выступает точкой входа для файловых данных, тогда как дальнейшая стоимостная оценка и агрегация вынесены в другие сервисы. Таким образом, импорт и нормализация изолированы от прайсинга и налогового расчёта и могут независимо развиваться и покрываться тестами.

3.4 Реализация сервиса исторического прайсинга

Сервис `price-svc` реализован на Go и является внутренним gRPC-сервисом для стоимостной оценки транзакций. Его основной публичный контракт состоит из методов `ValuateTransactionsBatch` и `UpsertTenantSymbol`.

Базовый сценарий работы сервиса следующий. На вход поступает пакет транзакций с указанием tenant, источника, целевой фиатной валюты и money legs. Для каждого актива необходимо определить канонический внешний идентификатор, получить историческую цену на момент операции и вернуть рассчитанное фиатное значение для входящего, исходящего и комиссионного legs.

Реализация сервиса разбита на несколько специализированных модулей. `internal/coingecko` отвечает за интеграцию с внешним источником криптовалютных цен. `internal/fiatfx` реализует пересчёт из USD в локальную фиатную валюту. На текущем этапе используется модель, в которой криптовалютная цена сначала определяется в USD, а затем при необходимости переводится в RUB, KZT и другие поддерживаемые фиатные валюты. `internal/usecases` содержит прикладную оркестрацию оценки, а `internal/server` — gRPC-слой.

Для повышения воспроизводимости и снижения нагрузки на внешние API сервис сочетает несколько уровней хранения и кэширования. Исторические цены записываются в PostgreSQL, быстро повторяемые запросы используют Redis, а редко меняющиеся справочные данные, например соответствие символов активов и `coin_id`, хранятся в in-memory структурах. Дополнительно поддерживаются tenant-specific symbol mappings: пользователь или бухгалтер может явно указать, какой внешний идентификатор должен использоваться для неоднозначного тикера. Для этого служит метод `UpsertTenantSymbol`.

С точки зрения прикладной логики важным результатом реализации `price-svc` стало отделение собственно получения цен от последующих этапов обработки транзакций. Это позволило вынести в отдельный сервис кэширование, обработку ошибок внешних провайдеров, разрешение неоднозначных символов и правила фиатной конвертации.

3.5 Реализация сервиса агрегации и read-model

Сервис `aggregation-svc` реализован на Go и отвечает за преобразование нормализованных транзакций из `ledger-svc` в агрегированную read-model, пригодную для просмотра, повторного чтения и последующего налогового расчёта.

Внешне сервис предоставляет через gRPC и grpc-gateway несколько ключевых интерфейсов:

1. `ListTransactionsByImport` — выдача агрегированных транзакций по import_id;
2. `ListTransactionsByRange` — выдача агрегированных транзакций по диапазону времени;
3. `GetTenantSettings` и `UpsertTenantSettings` — чтение и изменение tenant-настроек агрегации;
4. `ListSupportedFiatCurrencies` — выдача поддерживаемых фиатных валют.

Ключевой процесс внутри `aggregation-svc` запускается после завершения импорта в `ledger-svc`. Через RabbitMQ сервис получает событие об успешном импорте и начинает фоновую обработку. Далее он выполняет несколько шагов: получает транзакции по import_id из `ledger-svc`, загружает tenant-настройки, формирует батч-запрос в `price-svc`, получает стоимостную оценку и сохраняет результат в таблицу агрегированных транзакций.

На уровне кода этот сценарий оформлен как прикладной use case, а для защиты от повторной одновременной обработки одного и того же импорта используется lock manager. Это важно, так как доставка сообщений брокером может приводить к redelivery, а само состояние импорта должно оставаться согласованным.

Отдельно реализован сценарий on-the-fly переоценки транзакций при запросе в `ListTransactionsByRange`. Если в запросе передан `target_fiat`, отличный от tenant-настройки, сервис не изменяет сохранённую read-model в базе данных, а выполняет временную переоценку значений через `price-svc` только для выдачи ответа. Это решение оказалось важным для разделения пользовательских представлений и расчётного контура: пользователь может, например, смотреть агрегированную историю в одной валюте, а налоговый сервис может запросить ту же историю в валюте, соответствующей выбранной юрисдикции.

Ещё одна существенная часть реализации — хранение tenant-настроек. Для каждого tenant сервис хранит целевую фиатную валюту и временную зону, а также валидирует их при обновлении. Благодаря отдельному endpoint выдачи списка поддерживаемых валют внешний клиент может строить selector только по реально доступным кодам.

3.6 Реализация сервиса налогового расчёта

Сервис `tax-svc` реализован на Go и представляет собой оркестратор расчётного контура. Внешний интерфейс сервиса публикуется одновременно как gRPC-контракт и как REST API через `grpc-gateway`. На пользовательском уровне доступны методы чтения и изменения налогового профиля, создания задания на расчёт, получения статуса задания и получения списка ранее созданных заданий.

На уровне данных ключевыми сущностями являются `TaxProfile`, `TaxPolicy`, `TaxJob`, `TaxSummary`, а также набор событий и лотов, формируемых на этапе расчёта. `TaxProfile` хранит сведения о налогоплательщике и параметрах расчётного контура, `TaxPolicy` фиксирует политику конкретного запуска расчёта, а `TaxJob` является единицей выполнения фонового процесса.

Внутренний жизненный цикл расчёта организован через очередь заданий в базе. После вызова `StartReport` создаётся новый `TaxJob` в статусе `queued`. Фоновый воркер периодически вызывает атомарный метод захвата следующего задания и переводит одно queued-задание в `running`. Это гарантирует, что два воркера не начнут параллельно обрабатывать один и тот же расчёт.

Далее воркер выполняет последовательность действий:

1. загружает налоговый профиль пользователя;
2. определяет временные границы налогового года с учётом timezone профиля;
3. вычисляет целевую фиатную валюту на основе выбранной юрисдикции;
4. запрашивает у `aggregation-svc` агрегированные транзакции за нужный период и в нужной валюте;
5. выбирает расчётный движок через реестр `engines`;
6. запускает `Build`, который формирует промежуточный расчётный результат;
7. строит итоговую сводку `TaxSummary`;
8. формирует и сохраняет audit-артефакт в объектное хранилище;
9. сохраняет результат в `TaxJob`.

Расчётный контур специально отделён от внешнего API и инфраструктуры хранения. Для юрисдикций используется registry-подход: каждый движок реализует единый интерфейс `Engine`. На текущем этапе реализован RU-specific движок, который принимает на вход отсортированный список агрегированных транзакций, проверяет допустимость выбранного метода cost basis, классифицирует операции по `TxKind` и строит `BuildResult`. Этот промежуточный артефакт включает:

1. сформированные лоты;
2. события выбытия (`RealizationEvent`);
3. строки списания лотов (`RealizationLot`);
4. события дохода (`IncomeEvent`);
5. события расхода (`ExpenseEvent`);
6. строки списания расходов (`ExpenseLot`);
7. события перемещения (`MovementEvent`);
8. предупреждения, возникающие в ходе классификации.

Отдельно реализован retry-механизм для фонового воркера. Если ошибка вызвана временной недоступностью `aggregation-svc`, object storage или иным transient failure, задание не переводится сразу в `failed`, а ставится на повторную обработку. Для расчёта времени повторной попытки используется exponential backoff с full jitter. Это снижает вероятность синхронного повторного удара по недоступной зависимости и делает поведение системы более устойчивым.

Важный инженерный результат — перенос в объектное хранилище только стабильных `object keys` вместо временных presigned URL. В базе `tax-svc` сохраняются идентификаторы файлов, а на этапе чтения статуса задания сервис при необходимости генерирует новый временный URL. Это решение позволило устранить проблему хранения заведомо устаревающих ссылок в качестве источника истины.

Сервис также содержит отдельный клиент для `report-svc` и gRPC-контракт рендера отчёта. На текущем этапе этот контур подготовлен инфраструктурно, а основным сохраняемым артефактом расчёта является audit JSON. Финальная синхронная интеграция генерации итогового XML-отчёта выделена как следующий шаг развития расчётного контура.

3.7 Реализация сервиса формирования отчётного артефакта

Сервис `report-svc` выделен в отдельный backend-компонент, отвечающий за генерацию отчётного артефакта на основе подготовленного набора данных. В репозитории уже выделены proto-контракт сервиса, модуль работы с объектным хранилищем, слой генерации документа и инфраструктурные компоненты сервиса.

С инженерной точки зрения выделение `report-svc` в отдельный сервис является оправданным, поскольку:

1. логика расчёта и логика форматирования отчёта имеют различную природу;
2. генерация документов требует работы с шаблонами и файловыми артефактами;
3. объектное хранилище и файловые форматы не должны смешиваться с налоговым движком;
4. формат отчёта может развиваться независимо от расчётного контура.

На текущем этапе в сервисе уже подготовлены хранилищный слой, генератор документа и отдельные модели dataset, а также каркас обработки внутренних запросов. При этом итоговая синхронная схема взаимодействия `tax-svc -> report-svc -> object storage` рассматривается как целевая и требует окончательного согласования с обновлённой архитектурой налогового контура.

3.8 Контур API, наблюдаемость и локальный запуск

Практическая эксплуатация системы требует не только бизнес-логики, но и единого эксплуатационного контура. В проекте для этого реализованы несколько важных подсистем.

Во-первых, для Go-сервисов используется сочетание gRPC и grpc-gateway. Это позволяет иметь один внутренний строго типизированный контракт и одновременно публиковать внешний REST API без ручного дублирования обработчиков. Для Rust-сервисов `auth-svc` и `ledger-svc` внешние маршруты реализованы напрямую через `axum`.

Во-вторых, в проекте выделены OpenAPI-спецификации для frontend и internal API. Благодаря этому контракт между backend и frontend формализован отдельно от внутренних межсервисных вызовов. Это упростило документирование ошибок, маршрутов и заголовков tenant-контекста.

В-третьих, реализован контур наблюдаемости на основе OpenTelemetry, Prometheus, Loki и Grafana. Сервисы экспортируют структурированные логи, технические метрики и health-check статусы. Для gRPC-сервисов дополнительно включены `grpc_health_v1` и reflection, что упрощает отладку и проверку готовности сервисов.

В-четвёртых, для локального запуска и интеграционной проверки используется единый `docker-compose.yml`, который поднимает инфраструктурные зависимости проекта и дополнительные инструменты, например Swagger UI для просмотра OpenAPI-спецификаций. Такой подход оказался особенно полезен при проверке межсервисных сценариев: можно локально поднимать базы, очередь сообщений, object storage, а затем воспроизводить end-to-end поток обработки данных.

3.9 Результаты реализации и текущее состояние проекта

На текущем этапе разработки в проекте уже реализован значительный объём backend-функциональности.

Фактически завершены или доведены до рабочего состояния следующие части:

1. базовый auth-контур с регистрацией, подтверждением email, входом, ротацией токенов и logout;
2. сервис импорта CSV с поддержкой нескольких источников и выдачей транзакций по import_id;
3. сервис исторической оценки операций с gRPC batch valuation, кэшированием и tenant-specific symbol mapping;
4. сервис агрегации с фоновым потреблением импорта, сохранением read-model и on-the-fly переоценкой в альтернативный fiat;
5. налоговый сервис с профилем налогоплательщика, очередью заданий, retry-логикой, расчётным движком и сохранением audit-артефактов;
6. контур документации API, health-check, логирования и метрик;
7. общая инфраструктура локального запуска и интеграционной проверки.

При этом часть подсистем остаётся в активной доработке. В частности, контур `report-svc` уже выделен архитектурно и подготовлен на уровне контракта и инфраструктуры, однако окончательная синхронная интеграция генерации XML-отчёта с `tax-svc` требует завершения и согласования с текущей расчётной моделью. Аналогично, налоговый движок уже содержит реализованный каркас и RU-specific классификацию операций, но может быть расширен в сторону дополнительных юрисдикций и дальнейшей детализации правил расчёта.

Таким образом, программная реализация CryptoTax уже охватывает основную часть backend-конвейера: от аутентификации и импорта данных до прайсинга, агрегации, запуска расчёта и сохранения audit-результата. Это позволяет перейти от чисто архитектурного проектирования к полноценной интеграционной отладке системы и завершению оставшихся прикладных компонентов.

3.10 Выводы по главе 3

В данной главе была рассмотрена фактическая программная реализация системы CryptoTax. В отличие от предыдущей главы, посвящённой архитектурному проектированию и выбору технологий, здесь основное внимание было уделено тому, как эти решения воплощены в исходном коде и взаимодействующих сервисах.

Проведённый анализ показывает, что на текущем этапе в проекте уже сформирован работоспособный backend-контур, включающий:

1. сервис аутентификации и управления доступом;
2. сервис импорта и нормализации транзакций;
3. сервис исторической стоимостной оценки;
4. сервис агрегации и read-model;
5. сервис налогового расчёта и управления заданиями;
6. эксплуатационный контур наблюдаемости, документации API и локального запуска.

Ключевым практическим результатом является то, что архитектурные решения, обоснованные в предыдущих главах, не остались декларативными: они получили конкретное воплощение в виде изолированных сервисов, формализованных контрактов, хранилищных моделей, фоновых процессов и контуров интеграции. Одновременно реализация показала, что наиболее сложные области проекта — налоговый расчёт и генерация итогового отчётного документа — требуют отдельной поэтапной доводки и согласования прикладной логики с формальными контрактами сервисов.

Следовательно, текущая стадия проекта может быть охарактеризована как переход от архитектурного MVP к интеграционно зрелой backend-системе, в которой уже реализован основной конвейер обработки данных и выделены понятные направления дальнейшей доработки.
