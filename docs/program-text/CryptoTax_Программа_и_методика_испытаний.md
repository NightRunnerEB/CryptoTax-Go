1 ОБЪЕКТ ИСПЫТАНИЙ

1.1 Наименование программы

Наименование программы: «Веб-сервис для автоматизированной подготовки налоговой отчётности по операциям с криптовалютой».

Наименование программы на английском языке: «Web-service for Automated Cryptocurrency Tax Reporting Preparation».

Краткое наименование программы: «CryptoTax».

1.2 Краткая характеристика области применения программы

Программа является серверной частью системы CryptoTax, предназначенной для автоматизации обработки операций с криптовалютой и подготовки данных для расчёта налоговых обязательств. Система принимает пользовательские данные из внешних источников, приводит их к единому формату, обогащает историческими стоимостными оценками, формирует агрегированные представления операций, рассчитывает налоговые показатели и подготавливает итоговые отчётные артефакты.

В рамках backend-контура система состоит из набора взаимодействующих сервисов:

1. `auth-svc` — регистрация, вход, проверка и обновление токенов доступа;
2. `ledger-svc` — загрузка CSV-выгрузок, валидация, нормализация и хранение импортов и транзакций;
3. `price-svc` — получение исторических котировок и стоимостная оценка операций в целевой фиатной валюте;
4. `aggregation-svc` — формирование read-model по операциям, хранение tenant-настроек и выдача агрегированных транзакций;
5. `tax-svc` — хранение налогового профиля, создание и выполнение заданий на расчёт, формирование итоговых сводок и audit-артефактов;
6. `report-svc` — генерация отчётного артефакта на основе подготовленного результата расчёта.

Клиентский пользовательский интерфейс не является объектом испытаний данного документа. Испытания проводятся только для backend-компонентов системы, их API, внутренних интеграций и фоновых процессов.

3. корректность импорта, нормализации и выдачи транзакций;
4. корректность исторической стоимостной оценки операций;
5. корректность формирования агрегированных транзакций и tenant-настроек;
6. корректность создания, выполнения и выдачи результатов налоговых расчётов;

3 ТРЕБОВАНИЯ К ПРОГРАММЕ

3.1 Требования к функциональным характеристикам

Серверная часть системы CryptoTax должна обеспечивать возможность выполнения следующих функций.

Функции, обеспечивающие наблюдаемость и эксплуатацию системы:

1. запись структурированных логов приложений;
2. сбор и экспорт метрик сервисов;
3. предоставление health-check интерфейсов для сервисов;
4. корректную обработку и логирование ошибок.

Функции, обеспечивающие работу с пользователями и доступом:

1. регистрация пользователя;
2. подтверждение адреса электронной почты;
3. вход пользователя в систему;
4. обновление токенов доступа;
5. завершение пользовательской сессии;
6. проверка корректности аутентификационных данных и ограничение доступа к защищённым методам.

Функции, обеспечивающие импорт и нормализацию транзакций:

1. выдача списка поддерживаемых бирж;
2. загрузка CSV-файла поддерживаемого формата;
3. валидация структуры входного CSV-файла;
4. нормализация строк импорта в единую модель транзакции;
5. сохранение импорта и связанных транзакций;
6. выдача транзакций по конкретному импорту.

Функции, обеспечивающие стоимостную оценку операций:

1. пакетная оценка транзакций по историческим котировкам;
2. конвертация стоимости операций в поддерживаемую фиатную валюту;
3. сохранение и повторное использование исторических цен;
4. поддержка tenant-specific сопоставлений символов активов.

Функции, обеспечивающие агрегацию и read-model:

1. обработка события о завершении импорта;
2. загрузка нормализованных транзакций из сервиса импорта;
3. вызов сервиса прайсинга для оценки операций;
4. сохранение агрегированных транзакций;
5. выдача агрегированных транзакций по import_id;
6. выдача агрегированных транзакций по диапазону времени;
7. on-the-fly переоценка агрегированных транзакций в альтернативную фиатную валюту без изменения сохранённых данных;
8. получение и изменение tenant-настроек агрегации;
9. выдача списка поддерживаемых фиатных валют.

Функции, обеспечивающие налоговый расчёт:

1. получение налогового профиля tenant;
2. создание или обновление налогового профиля tenant;
3. валидация налогового профиля;
4. создание задания на расчёт налогового отчёта;
5. атомарный захват queued-задания воркером;
6. повторные попытки обработки задания при временных отказах внешних зависимостей;
7. запрос агрегированных транзакций из aggregation-svc;
8. расчёт налогового результата на основе выбранной политики;
9. формирование и сохранение audit-артефакта;
10. выдача статуса задания;
11. выдача списка заданий с пагинацией;
12. генерация временных presigned URL на этапе чтения статуса задания.

Функции, обеспечивающие генерацию отчётных артефактов:

1. получение синхронного внутреннего запроса от tax-svc на формирование отчёта;
2. загрузка подготовленного dataset из объектного хранилища;
3. генерация итогового отчётного артефакта;
4. сохранение итогового артефакта в объектное хранилище;
5. возврат в tax-svc object key сформированного отчётного артефакта или описания ошибки.

Функции, обеспечивающие межсервисное взаимодействие:

1. синхронные вызовы между сервисами по gRPC;
2. асинхронная обработка событий через RabbitMQ в тех контурах, где она предусмотрена архитектурой системы;
3. передача tenant-контекста в межсервисных запросах;
4. корректная обработка ошибок зависимых сервисов.

3.2 Требования к интерфейсу

Визуальный интерфейс у программы не является объектом испытаний.

Программный интерфейс системы должен представлять собой:

1. REST API для внешних пользовательских и управляющих операций;
2. gRPC API для внутренних типобезопасных межсервисных вызовов;
3. JSON как основной формат передачи данных для REST-запросов и ответов;
4. Protocol Buffers как формат описания и передачи данных для gRPC-взаимодействия;
5. заголовки tenant-контекста (`X-User-Id`, при необходимости `X-User-Id`, `X-Roles`) для tenant-scoped запросов.

3.3 Требования к обеспечению надёжного функционирования программы

1. Система должна корректно обрабатывать неверные запросы любого вида и выдавать информативные сообщения об ошибках.
2. В случае ошибки при обработке одного запроса или одного фонового задания система должна продолжать корректно функционировать для остальных запросов.
3. Ошибки внешних зависимостей должны быть локализованы и не должны приводить к некорректному состоянию данных.
4. При повторной обработке событий и повторных вызовах система должна сохранять идемпотентное поведение в предусмотренных сценариях.
5. Данные в объектном хранилище, базах данных и очередях сообщений должны использоваться согласованно, без записи временных ссылок как основного источника истины.

3.4 Требования к восстановлению после отказа

При отказе, который произошёл по вине внешних факторов и не является непоправимым, время восстановления не должно превышать времени, необходимого для перезапуска контейнеров, инфраструктурных зависимостей и сервисов системы.

Если отказ был вызван временной недоступностью зависимого сервиса или инфраструктурного компонента, система должна:

1. фиксировать ошибку в журнале;
2. по возможности выполнять повторную попытку обработки в фоновом контуре;
3. не терять уже сохранённые корректные данные;
4. после восстановления зависимости продолжать выполнение от последнего согласованного состояния.

Для предотвращения отказов вследствие некорректного ввода данных должны быть предусмотрены проверки формата входных данных, обязательных полей, UUID-идентификаторов, tenant-заголовков, параметров пагинации, допустимых кодов валют, а также требований к налоговому профилю.

6.3 Проверка требований к функциональным характеристикам

6.3.1 Запись структурированных логов приложений

1. При запуске каждого сервиса в stdout должны записываться структурированные логи в машиночитаемом формате.
2. При успешной обработке запроса должен формироваться лог-запись с указанием метода, длительности и статуса обработки.
3. При ошибке обработки запроса или фонового задания должна формироваться лог-запись с кодом и описанием ошибки.

6.3.2 Сбор метрик и health-check статусов

1. После запуска сервисов должны быть доступны health-check интерфейсы.
2. При обработке запросов должны формироваться метрики количества и длительности вызовов.
3. Метрики должны быть доступны через настроенный контур наблюдаемости и пригодны для последующего просмотра в Grafana.

6.3.3 Регистрация пользователя

1. При отправке запроса регистрации с корректным email и паролем должен создаваться новый пользователь.
2. При попытке зарегистрировать пользователя с уже существующим email должна возвращаться ошибка конфликта.
3. При передаче некорректного email или недопустимого пароля должна возвращаться ошибка валидации.

6.3.4 Подтверждение адреса электронной почты

1. При обращении к endpoint подтверждения с корректным одноразовым токеном должен возвращаться успешный ответ.
2. При обращении с недействительным или просроченным токеном должна возвращаться ошибка авторизации или валидации.

6.3.5 Вход пользователя в систему

1. При отправке корректных учётных данных должен возвращаться успешный ответ с access и refresh токенами.
2. При отправке неверных учётных данных должна возвращаться ошибка авторизации.
3. При входе пользователя, не прошедшего необходимые проверки доступа, должна возвращаться ошибка авторизации или запрета доступа.

6.3.6 Обновление токенов доступа

1. При отправке корректного refresh токена должен возвращаться новый набор токенов.
2. При отправке некорректного или отозванного refresh токена должна возвращаться ошибка авторизации.

6.3.7 Завершение пользовательской сессии

1. При обращении к endpoint logout с корректным access токеном пользовательская сессия должна завершаться.
2. После завершения сессии повторное использование отозванного токена должно приводить к ошибке авторизации.

6.3.8 Получение списка поддерживаемых бирж

1. При обращении к endpoint `/v1/exchanges/supported` должен возвращаться успешный ответ со списком поддерживаемых бирж.
2. Возвращаемый список не должен быть пустым, если в системе сконфигурирован хотя бы один поддерживаемый импортёр.

6.3.9 Импорт CSV-файла поддерживаемого формата

1. При загрузке корректного CSV-файла поддерживаемой биржи должен создаваться новый импорт.
2. В результате обработки должны формироваться нормализованные транзакции, доступные для последующего получения.
3. В ответе на успешный импорт должна возвращаться информация, достаточная для идентификации результата обработки.

6.3.10 Обработка некорректного CSV-файла

1. При загрузке файла без обязательных колонок должна возвращаться ошибка валидации.
2. При загрузке файла с неверным форматом данных в строках должна возвращаться ошибка валидации с описанием причины.
3. Некорректный импорт не должен приводить к сохранению частично повреждённых данных как корректного результата.

6.3.11 Выдача транзакций по импорту в ledger-svc

1. При обращении к внутреннему endpoint `/v1/imports/{import_id}/transactions` с корректным header `X-User-Id` для существующего импорта должен возвращаться список нормализованных транзакций.
2. При обращении с несуществующим import_id должна возвращаться ошибка not found.
3. При обращении с отсутствующим или некорректным `X-User-Id` должна возвращаться ошибка авторизации/валидации.

6.3.12 Пакетная стоимостная оценка транзакций в price-svc

1. При отправке корректного gRPC-запроса `ValuateTransactionsBatch` должен возвращаться успешный ответ с рассчитанными значениями для входящих, исходящих и комиссионных legs.
2. Для каждой оценённой транзакции должен возвращаться результат, соответствующий идентификатору переданной транзакции.
3. При невозможности оценить актив должен возвращаться диагностический результат с указанием причины ошибки.

6.3.13 Обработка неподдерживаемой фиатной валюты в price-svc

1. При отправке запроса оценки с неподдерживаемым кодом фиатной валюты должна возвращаться ошибка invalid argument.
2. Ошибка должна содержать достаточное описание, позволяющее понять, что указанная фиатная валюта не поддерживается.

6.3.14 Tenant-specific сопоставление символов активов

1. При вызове `UpsertTenantSymbol` с корректными параметрами должно сохраняться новое сопоставление символа и coin_id.
2. После сохранения сопоставления повторная оценка транзакции с данным символом должна использовать новое соответствие.

6.3.15 Обработка события завершения импорта в aggregation-svc

1. После публикации события об успешном импорте aggregation-svc должен получить данные транзакций из ledger-svc.
2. Для полученных транзакций должен быть вызван price-svc для стоимостной оценки.
3. По завершении обработки в базе aggregation-svc должны появиться агрегированные транзакции, связанные с исходным import_id.

6.3.16 Получение tenant-настроек агрегации

1. При первом обращении к `GetTenantSettings` для tenant без сохранённых настроек должен возвращаться корректный объект настроек по умолчанию.
2. При обращении к `GetTenantSettings` для tenant с сохранёнными настройками должны возвращаться актуальные значения fiat_currency и timezone.

6.3.17 Изменение tenant-настроек агрегации

1. При отправке корректного запроса `UpsertTenantSettings` должны сохраняться новые значения fiat_currency и timezone.
2. При отправке неподдерживаемого fiat_currency должна возвращаться ошибка invalid argument.
3. При отправке некорректной timezone должна возвращаться ошибка invalid argument.

6.3.18 Получение списка поддерживаемых фиатных валют

1. При обращении к endpoint `/v1/fiat-currencies` должен возвращаться успешный ответ со списком поддерживаемых фиатных валют.
2. Для каждой валюты должен возвращаться нормализованный код и отображаемое имя.

6.3.19 Выдача агрегированных транзакций по import_id

1. При обращении к `ListTransactionsByImport` для существующего tenant и import_id должен возвращаться список агрегированных транзакций.
2. Возвращаемый список должен содержать поля времени, типа операции, источника, а также оценённые money legs.
3. При передаче некорректных параметров пагинации должна возвращаться ошибка валидации.

6.3.20 Выдача агрегированных транзакций по диапазону времени

1. При обращении к `ListTransactionsByRange` с корректным диапазоном времени должен возвращаться список агрегированных транзакций в указанном интервале.
2. При передаче некорректного временного диапазона должна возвращаться ошибка валидации.
3. При отсутствии tenant-заголовка должна возвращаться ошибка валидации.

6.3.21 Переоценка агрегированных транзакций в альтернативный fiat

1. При обращении к `ListTransactionsByRange` с параметром `target_fiat`, отличающимся от сохранённой tenant-настройки, должны возвращаться те же транзакции, но с on-the-fly переоценёнными фиатными значениями.
2. При этом сохранённые в базе aggregation-svc read-model данные не должны изменяться.
3. При указании неподдерживаемого `target_fiat` должна возвращаться ошибка invalid argument.

6.3.22 Получение налогового профиля

1. При обращении к `GetTaxProfile` для tenant с существующим профилем должен возвращаться сохранённый профиль.
2. При обращении к `GetTaxProfile` для tenant без профиля должна возвращаться ошибка not found.

6.3.23 Создание или обновление налогового профиля

1. При отправке корректного запроса `UpsertTaxProfile` должен сохраняться профиль налогоплательщика.
2. При передаче некорректного user_id должна возвращаться ошибка invalid argument.
3. При передаче пустых обязательных полей профиля должна возвращаться ошибка invalid argument.
4. При передаче некорректного timezone, tax_residency_status или taxpayer_type должна возвращаться ошибка invalid argument.

6.3.24 Создание задания на налоговый расчёт

1. При отправке корректного запроса `StartReport` должен создаваться новый TaxJob в статусе `queued`.
2. В созданном задании должны фиксироваться user_id, tax_year, policy_snapshot, количество попыток и время создания.
3. При отсутствии налогового профиля для tenant должна возвращаться ошибка not found.
4. При передаче некорректных параметров tax_year или tax_policy должна возвращаться ошибка invalid argument.

6.3.25 Захват и выполнение queued-задания воркером tax-svc

1. Фоновый воркер должен атомарно переводить одно queued-задание в статус `running`.
2. При успешном выполнении расчёта статус задания должен изменяться на `success`.
3. В результате выполнения должны формироваться сводные показатели расчёта и audit-артефакт.

6.3.26 Повторные попытки обработки задания при временных отказах

1. При временной недоступности aggregation-svc или object storage задание не должно окончательно завершаться с первой неудачной попытки.
2. Для задания должна быть назначена повторная попытка выполнения с увеличением счётчика attempts.
3. После восстановления зависимого сервиса задание должно быть успешно обработано в пределах допустимого количества попыток.

6.3.27 Получение статуса задания на расчёт

1. При обращении к `GetReportStatus` для существующего задания должен возвращаться актуальный статус, summary и диагностическая информация.
2. При обращении с несуществующим report_id должна возвращаться ошибка not found.
3. Если для задания существуют object keys артефактов, на этапе чтения должны формироваться временные presigned URL.

6.3.28 Получение списка заданий на расчёт

1. При обращении к `ListReports` должен возвращаться список заданий указанного tenant с учётом параметров пагинации.
2. Возвращаемый total должен соответствовать общему количеству заданий tenant.
3. При передаче некорректных параметров пагинации должна возвращаться ошибка invalid argument.

6.3.29 Сохранение audit-артефакта в объектном хранилище

1. При успешном завершении расчёта audit-артефакт должен быть сохранён в MinIO.
2. В базе tax-svc должен сохраняться object key, а не временная ссылка.
3. При последующем чтении статуса задания должна генерироваться новая временная ссылка на скачивание артефакта.

6.3.30 Генерация отчётного артефакта в report-svc

1. При отправке корректного синхронного внутреннего запроса из tax-svc report-svc должен скачать dataset из объектного хранилища.
2. На основе dataset должен быть сформирован итоговый отчётный артефакт.
3. Итоговый артефакт должен быть загружен в объектное хранилище, а в ответ tax-svc должен быть возвращён object key сформированного отчёта.
4. При ошибке загрузки dataset, генерации или сохранения артефакта report-svc должен вернуть tax-svc ошибку с описанием причины отказа.

6.3.31 End-to-end сценарий «импорт → агрегация»

1. После загрузки корректного CSV в ledger-svc должен создаваться import.
2. После завершения импорта aggregation-svc должен получить событие и сформировать агрегированные транзакции.
3. Агрегированные транзакции должны быть доступны через соответствующие API read-model.

6.3.32 End-to-end сценарий «налоговый расчёт → отчётный артефакт»

1. После создания налогового задания tax-svc должен перевести его в queued, затем в running и далее в success при успешной обработке.
2. В ходе обработки должны быть получены агрегированные транзакции, рассчитан результат и сформирован audit-артефакт.
3. В рамках выполнения tax job tax-svc должен синхронно вызвать report-svc для генерации отчётного артефакта.
4. После завершения полного контура у задания должны быть доступны summary, audit object key и ссылка на отчётный артефакт.

ПРИЛОЖЕНИЕ 1 ТЕРМИНОЛОГИЯ

API (англ. Application Programming Interface) – программный интерфейс, через который один компонент системы взаимодействует с другим.

REST API – архитектурный стиль взаимодействия по HTTP, используемый для внешних запросов к backend-системе.

gRPC – протокол и технология удалённых вызовов процедур, используемая в системе для внутренних типобезопасных межсервисных вызовов.

Protocol Buffers – язык и бинарный формат сериализации данных, применяемый для описания и передачи gRPC-сообщений.

Tenant – изолированный контекст данных конкретного пользователя или организации в системе.

Read-model – специально подготовленное представление данных, оптимизированное для чтения и выдачи клиенту.

Audit-артефакт – детализированный результат расчёта, содержащий входные данные, шаги обработки и итоговые показатели, пригодный для последующей проверки.

Object key – стабильный идентификатор объекта в объектном хранилище.

Presigned URL – временная ссылка на скачивание объекта из объектного хранилища.

Health-check – интерфейс, позволяющий проверить готовность сервиса к обработке запросов.
